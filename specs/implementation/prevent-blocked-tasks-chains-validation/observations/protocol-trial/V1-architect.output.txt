## Decision

Two code-planning scopes: **(1) client capture + local durable persistence** and **(2) backend sync/ingestion**, connected by a record interface where a client-observed timestamp and a server-assigned timestamp are kept as two distinct fields — because the goal is silent on clock synchronisation and durability-before-leaving-site forces offline capture, I will not assert that device clocks are trustworthy or synchronized.

### Component boundaries

| Component | Responsibility |
|---|---|
| **Capture Client** (mobile browser) | Scan object code, assemble a work record, write it to local durable storage synchronously, before any network call and before the user is told it's saved. |
| **Local Durable Store** | Browser-native persistence (e.g. IndexedDB) that survives tab close/reload without a server round-trip. Owns the "durable before leaving site" guarantee. |
| **Sync Agent** (client, background) | Drains the local store opportunistically when connectivity exists; delivers records to the backend; retries idempotently. |
| **Ingestion Endpoint** (backend) | Accepts records, assigns authoritative receipt time, deduplicates by client-generated record ID. |

### Interface contract: Work Record

Crosses the Capture Client → Local Durable Store → Sync Agent → Ingestion Endpoint boundary unchanged except for one field added at ingestion:

- `record_id` (client-generated, unique) — dedup key across retries.
- `object_code` — scan payload.
- `capture_time` — **client device clock at scan time.**
- `ingested_at` — **added by the backend on receipt.** Absent until synced.

### Guarantees introduced (and source)

| Guarantee | Source |
|---|---|
| Record write completes to local durable storage before the user can leave the capture flow | Goal spec, `specs/goal.md#Scope` — "records must be durable before the worker leaves the site" (direct) |
| A record has a `capture_time` populated from the client device clock | **ASSUMPTION**, architect-introduced. Not in goal. Forced by the durability requirement: an authoritative server timestamp cannot exist until sync, and sync cannot be required for durability without contradicting the site-departure guarantee. |
| `capture_time` is **not** claimed to be accurate, monotonic across devices, or synchronized | **ASSUMPTION**, architect-introduced, precisely because the goal is silent on clock sync. I am deliberately not asserting a guarantee the spec doesn't support. |
| `ingested_at` (server-assigned) is the authoritative time for any cross-device ordering | **DERIVED** from the above — if `capture_time` can't be trusted, ordering-sensitive consumers need a time source that can. This is a structural consequence, not a spec requirement. |
| Records eventually reach a backend/ingestion point, not just the device | **DERIVED**, not explicit in the quoted goal text ("durable" is only specified relative to leaving the site). Flagged below as an Open Question rather than silently built in. |

### Open Questions (unresolved from spec, need goal-owner decision)

1. Is a backend ingestion/sync scope actually in CAP-2, or does "durable" mean local-only and sync is a separate capability? I've assumed sync is in scope because a record that never leaves the device has no described business use, but the quoted goal text only commits to local durability.
2. Does anything downstream (audit, billing, dispute resolution) depend on `capture_time` being correct? If yes, this architecture is insufficient as-is and needs a trusted-time strategy (e.g., signed server challenge before scan, or explicit "best-effort, unverified" labeling surfaced to end users/auditors) — that's a product decision the goal spec doesn't make.

I'm not blocking on these — proceeding with the dual-timestamp design keeps both scopes buildable and reversible; nothing here forecloses either answer.
