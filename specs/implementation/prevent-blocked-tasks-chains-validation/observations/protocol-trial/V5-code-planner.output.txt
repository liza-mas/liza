## Origin of each edge

All four children were created in one transition — cp-3 depends on `cp-access`, and cp-access produced exactly one output (`doc-1`). Per the `inherit_inputs` rule, `inherit_inputs: null` (the default) means *"this child waits for every child of every upstream task this task depends on."* Since none of the four children set `inherit_inputs`, the transition engine gave **all of them** an edge to the sole cp-access output (`doc-1`), regardless of whether they actually consume it.

So the edges are mechanically identical in origin (default inheritance from cp-3→cp-access resolution), but only one is semantically justified:

| Task | Edge origin | Semantically needed? |
|---|---|---|
| code-3-1 (Records table migration) | default `inherit_inputs=null` blanket inheritance | No |
| code-3-2 (Access adapter) | default `inherit_inputs=null` blanket inheritance | **Yes** — consumes the interface doc |
| code-3-3 (Scan UI) | default `inherit_inputs=null` blanket inheritance | No |
| code-3-4 (Sync worker) | default `inherit_inputs=null` blanket inheritance | No |

There's no evidence any of code-3-1/3/4 declared a real need for `doc-1` — the edge exists purely as a side effect of the inheritance default, not a stated requirement.

## Proposed repair

Drop the `doc-1` edge from code-3-1, code-3-3, code-3-4 (letting them proceed — they're already `READY` otherwise); keep it on code-3-2, which stays legitimately blocked until `doc-1` clears. This is a dependency-graph repair, so it must go through the command-free `apply-dependency-repair` request, not ad hoc `mark-blocked --repair-*` flags:

```
PROPOSE: liza mark-blocked cp-3 --agent-id code-planner-1 \
  --reason "Default inherit_inputs blanket-inherited doc-1 to all four cp-3 children; only code-3-2 consumes the interface. Requesting removal of the doc-1 dependency edge for code-3-1, code-3-3, code-3-4." \
  --questions "Confirm code-3-1/3-3/3-4 have no other undeclared need for the access-interface doc before edges are dropped." \
  --repair-request-file repair-cp3-doc1.json --json
```

`repair-cp3-doc1.json`:
```json
{
  "type": "apply-dependency-repair",
  "task": "cp-3",
  "remove_edges": [
    {"from": "code-3-1", "to": "doc-1"},
    {"from": "code-3-3", "to": "doc-1"},
    {"from": "code-3-4", "to": "doc-1"}
  ],
  "keep_edges": [
    {"from": "code-3-2", "to": "doc-1"}
  ],
  "rationale": "Blanket inherit_inputs=null edge from cp-3→cp-access resolution applied doc-1 to all four children; only code-3-2 (access adapter) semantically consumes the access-interface documentation."
}
```

Caveat: `cp-3` is not my assigned task (I hold `task-1`), so I have no authority to submit this mutation myself — it belongs to whichever code-planner/owner holds `cp-3`. I'm surfacing origin + repair per the request, not executing it.
