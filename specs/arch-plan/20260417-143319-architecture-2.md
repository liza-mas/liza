# Architecture Plan — Plan-Time Detection & Context Enrichment for Pre-Commit Bootstrap

**Task:** architecture-2
**Goal spec:** `specs/goals/20260417-precommit-bootstrap.md`
**Section:** Q2 — Idempotency / plan-time & execution-time dedup
**Scope of this plan:** (a) new `internal/precommit/` package with `ConfigExistsOnIntegration` and `BootstrapInFlight` helpers, (b) `RoleContextData` extended with `PreCommitConfigExists` / `PreCommitBootstrapInFlight` booleans populated only for the architect role, (c) error propagation from helper failure to an explicit task-blocking orchestrator outcome (BLOCKED), (d) test plan for exists/absent/error and BLOCKED-in-flight counted as in-flight.

**Out of scope (owned by architecture-1, already MERGED):** `kind` field on `OutputEntry` / `Task`, `proceed.go` authoritative dedup, `replan.go` propagation, round-trip unit tests for `Kind`. This plan reuses the `Kind` field specified by that plan's §2.1/§2.2.

**Also out of scope (sibling tasks in the overall bootstrap implementation):** architect prompt template additions, `base_prompt.tmpl:36` rewording, ADR-0036 amendment or supersede, bootstrap task's `done_when` phrasing, greenfield reproduction run.

## 1. Component Boundaries & Responsibilities

| Component | File(s) | Responsibility |
|-----------|---------|----------------|
| Detection package | `internal/precommit/precommit.go` (new), `internal/precommit/precommit_test.go` (new) | Expose two pure detection helpers — one integration-branch file check, one repo-wide scan by `Kind` marker. Package has no knowledge of prompts, templates, or task lifecycle. |
| Context builder | `internal/agent/prompt.go` (`buildTaskRoleContextData`) | Call the two helpers only when the target role is `architect`; populate `RoleContextData.PreCommitConfigExists` / `PreCommitBootstrapInFlight`. Surface helper errors to the caller. |
| Role-context data | `internal/prompts/role_context.go` (`RoleContextData`) | Carry two new booleans in the architect field group. No rendering, no logic. |
| Prompt orchestration | `internal/agent/prompt.go` (`buildPromptWithContext`), `internal/agent/strategy_doer.go` (`BuildPrompt`), `internal/agent/supervisor.go` (the `BuildPrompt` call site at L817) | Propagate the helper error upward and translate it into a BLOCKED task outcome via the existing `blockTaskFromSupervisor` primitive. |
| Test surface | `internal/precommit/precommit_test.go`, `internal/agent/prompt_test.go` | Cover exists / absent / error on `ConfigExistsOnIntegration`; cover non-terminal hit (including BLOCKED) / miss / empty-kind skip on `BootstrapInFlight`; cover architect-only population and error-propagation path through the context builder. |

**Non-responsibilities:**

- The `precommit` package does **not** render template blocks. The two booleans feed prompt-template conditionals authored in a sibling task — this plan only ensures the data reaches `RoleContextData`.
- The package does **not** decide what "`bootstrap-precommit`" means. The `Kind` string constant is defined next to the helper (one-line, documented as mirroring the architect-prompt marker) and consumed locally; `proceed.go` remains agnostic per architecture-1 §2.
- The context builder does **not** itself mark the task BLOCKED. Blocking is the supervisor's responsibility, reusing `blockTaskFromSupervisor` (`supervisor.go:289`).
- The helper is **not** a `pipeline.Resolver` responsibility (goal spec §Q2, "Terminology"). Keep the package boundary distinct.

## 2. Package Layout — `internal/precommit/`

### 2.1 File layout

```
internal/precommit/
    precommit.go         — package doc + Kind constant + two exported helpers
    precommit_test.go    — unit tests (§5.1–§5.6)
```

Single-file package. No sub-packages. Matches the weight of existing single-purpose packages such as `internal/gitenv/` (one file, ~30 lines) and `internal/paths/` (small set of normalizers).

### 2.2 Package declaration and `Kind` constant

```go
// Package precommit provides repo-state detection helpers for the
// pre-commit bootstrap planning step: checking whether the integration
// branch already carries .pre-commit-config.yaml, and whether a
// bootstrap task is already in flight anywhere in the state.
package precommit

// Kind is the typed marker value (see architecture-1 §2.1) that the
// architect emits on output[].kind and that proceed.go treats as the
// authoritative dedup key. Exported so callers can reuse the same
// literal and so the bootstrap task creation / dedup / detection code
// paths cannot drift on the string.
const Kind = "bootstrap-precommit"
```

The `Kind` constant lives in this package because the detection helpers are the primary consumer (`BootstrapInFlight` needs the exact value). The architect prompt template (sibling task) and the bootstrap task's `done_when` phrasing (sibling task) both import this constant rather than hard-coding a second copy. `internal/ops/proceed.go` remains agnostic — it compares `Kind`s structurally, not against this constant (per architecture-1 §1 non-responsibility "proceed.go does not know the string `bootstrap-precommit`").

### 2.3 `ConfigExistsOnIntegration`

```go
// ConfigExistsOnIntegration reports whether .pre-commit-config.yaml
// exists at the tip of the integration branch in the given project
// root.
//
// Implementation uses `git cat-file -e <branch>:.pre-commit-config.yaml`
// so it reads committed state, not the working tree. A working-tree
// read would pick up uncommitted human drift (or in-progress worktree
// changes from a sibling coding task) and give a false positive.
// Precedent: checkSpecFileExists in internal/statevalidate/validate.go:92
// uses the same plumbing for the same reason, falling back to
// `git cat-file -e` when the filesystem check is insufficient.
//
// Returns (false, nil) when the branch or ref exists and the file does
// not. Returns (true, nil) when the file is present. Returns (_, err)
// only for plumbing failures that prevent a reliable answer (git not
// on PATH, branch missing, plumbing exit status other than 0 or 1, IO
// error while capturing stderr).
func ConfigExistsOnIntegration(projectRoot, integrationBranch string) (bool, error)
```

| Aspect | Spec |
|--------|------|
| Path checked | Literal `.pre-commit-config.yaml` at repo root of `integrationBranch`. Not configurable in this plan — the contract template (`commit_workflow.tmpl`) assumes that exact name, so a configurable path would introduce drift without a caller need. |
| Absolute-path guard | If `projectRoot` is empty, return `(false, error)` — configuration invariant violated, not a "file absent" answer. |
| Empty-branch guard | If `integrationBranch` is empty, return `(false, error)`. Same reason: the caller must pass a real branch (reviewer verifies). |
| Plumbing cmd | `gitenv.Command("cat-file", "-e", integrationBranch+":.pre-commit-config.yaml")` with `cmd.Dir = projectRoot`. Uses the shared `gitenv.Command` wrapper so `LC_ALL=C` is set — stderr parsing stays locale-stable. |
| Exit-code semantics | `git cat-file -e` exits 0 if the object exists, 1 if it does not, other codes for real errors. The helper distinguishes: 0 → `(true, nil)`; 1 with stderr empty or matching the well-known "not a valid object name" / "does not exist" pattern → `(false, nil)`; any other exit code, or exit 1 with unexpected stderr, → `(false, err)` wrapping stderr. |
| Logging | None. The helper is a pure function over git state. Diagnostic context belongs to the caller (the context builder wraps the error). |
| Symlink / LFS | Not handled. `.pre-commit-config.yaml` is a regular file in every supported project; if a future project stores it differently, that is a separate design question. |

Precedent and divergence from `checkSpecFileExists` (`internal/statevalidate/validate.go:92`):

- Precedent reused: `gitenv.Command("cat-file", "-e", <branch>:<path>)` with `cmd.Dir = projectRoot`.
- Divergence 1: `checkSpecFileExists` falls back to `git cat-file -e` **after** `os.Stat`. Here we do **not** consult the filesystem first, because we explicitly want to ignore working-tree drift (goal spec §Q2: "not direct filesystem read of the main working tree, which may include uncommitted human drift").
- Divergence 2: `checkSpecFileExists` treats any non-zero exit from git as "file not found" and returns a generic error. Here we must differentiate "file absent" (`false, nil`) from "plumbing failed" (`false, err`) so the context-builder can take different actions (omit bootstrap vs block the task). The exit-code distinction on `cat-file -e` is stable and documented in `git-cat-file(1)`.

### 2.4 `BootstrapInFlight`

```go
// BootstrapInFlight reports whether any task in the given state has
// Kind == precommit.Kind and a non-terminal status. "Non-terminal"
// here means Task.Status.IsTerminal() returns false — which excludes
// MERGED, ABANDONED, SUPERSEDED and includes BLOCKED (a blocked
// bootstrap will eventually merge once rescoped, so it genuinely is
// in flight; see goal spec §Q2 "Rescope invariant").
//
// Repo-wide: scans state.Tasks with no filter by Goal / Sprint. Two
// concurrent goals racing to emit bootstrap see each other via this
// scan; cross-goal parallelism is covered by construction. This
// mirrors the same design property in collectNonTerminalByKind
// (architecture-1 §3.2), and deliberately shares no code with it —
// the prompt-time read path runs outside proceed.go's Modify
// callback, so coupling the two would be a layering error.
func BootstrapInFlight(state *models.State) bool
```

| Aspect | Spec |
|--------|------|
| Input | Non-nil `*models.State`. On `nil` input, returns `false` — callers build their own state from disk before invoking this helper; a nil state is programmer error, not a runtime condition. No panic, no error (this helper does not return error — the scan is pure in-memory and cannot fail). |
| Scan cost | O(len(state.Tasks)). `state.Tasks` is already loaded in memory by the context builder. No new IO. |
| Terminal definition | `task.Status.IsTerminal()` (`models.Task.Status`, `task.go:146`). MERGED / ABANDONED / SUPERSEDED → terminal; every other status (including BLOCKED, DRAFT_*, IMPLEMENTING_*, IN_REVIEW, INTEGRATION_*, etc.) → in flight. |
| Empty-Kind skip | Tasks with `Kind == ""` are not candidates — same invariant as `proceed.go`'s scan (architecture-1 §3.2). |
| Early exit | Loop breaks on first match. Result is a boolean, not a list; the context builder only needs to know "is there at least one". |
| Concurrency | None. The caller passes a snapshot `*models.State` obtained through the normal `blackboard` read path. TOCTOU between the plan-time check and the later proceed-time dedup is acceptable and explicitly covered by the goal spec ("B is not sufficient on its own"); the authoritative dedup lives in `proceed.go` per architecture-1. |

### 2.5 Why no `ListBootstrapInFlight`?

A helper returning the list of matching task IDs would be needed only if the architect prompt surfaced incumbent IDs or if a later caller wanted to warn about orphaned multiples. Neither is in scope. YAGNI — add the richer primitive if and when a second caller appears.

## 3. `RoleContextData` Extension

### 3.1 New fields (`internal/prompts/role_context.go`)

Add to `RoleContextData`, placed in the existing "Architecture-specific" group (right after `ParentTaskContexts`, `role_context.go:66`):

```go
    // Architecture-specific (populated for architect role)
    ParentTaskContexts      []ParentTaskContext
    PreCommitConfigExists   bool
    PreCommitBootstrapInFlight bool
```

| Aspect | Spec |
|--------|------|
| Field names | `PreCommitConfigExists`, `PreCommitBootstrapInFlight`. Go-idiomatic: start with the domain prefix (`PreCommit`) so template authors can disambiguate at a glance among future bootstrap-related fields. |
| Type | `bool`. A tri-valued type (present / absent / unknown) is unnecessary because helper errors never become "unknown in the template" — they short-circuit into BLOCKED (§4). |
| Default | `false` (Go zero). For non-architect roles the helpers are never called, so both fields stay `false`. Template blocks that render these fields MUST gate on the architect role anyway (`{{- if eq .Role "architect" -}}`), so a non-architect zero-value never leaks. |
| Placement | Grouped with the existing architect-specific block (`ParentTaskContexts`). Keeps all architect fields in one contiguous region for readability and so future context-section migrations (ADR-0036/0056 follow-ups) have a clear anchor. |
| Rendering | **Not owned by this plan.** Template blocks that consume these fields are a sibling task. The field surface is final; any rendering decisions layer on top of it. |

### 3.2 Population path (`internal/agent/prompt.go`, `buildTaskRoleContextData`)

Current signature (prompt.go:113):

```go
func buildTaskRoleContextData(task *models.Task, state *models.State, config SupervisorConfig, resolver *pipeline.Resolver) *prompts.RoleContextData
```

New signature:

```go
func buildTaskRoleContextData(task *models.Task, state *models.State, config SupervisorConfig, resolver *pipeline.Resolver) (*prompts.RoleContextData, error)
```

Signature change justified because §4 requires callers to distinguish "context built" from "detection plumbing failed". An in-band sentinel on the struct (e.g. a third `err` field) would require every template block and every test to guard on it; an explicit `error` is the idiomatic Go way and matches `buildPromptWithContext`'s already-error-returning signature.

**Architect-only gating.** Add a new block immediately after the existing "Architect-specific: parent task contexts" block (prompt.go:211-225):

```go
    // Architect-specific: pre-commit bootstrap context
    if config.Role == roles.Architect {
        exists, err := precommit.ConfigExistsOnIntegration(config.ProjectRoot, state.Config.IntegrationBranch)
        if err != nil {
            return nil, fmt.Errorf("precommit config check: %w", err)
        }
        data.PreCommitConfigExists = exists
        data.PreCommitBootstrapInFlight = precommit.BootstrapInFlight(state)
    }
```

| Aspect | Spec |
|--------|------|
| Role gating | `config.Role == roles.Architect`. Uses the canonical `roles.Architect` constant (`internal/roles/roles.go:27`). Non-architect roles skip both helpers; both fields remain zero. |
| Placement | **After** `ParentTaskContexts` population (prompt.go:211-225). If either helper errors, we still abort the build — it is not the existing architect-context block's error (different failure domain), but grouping all architect-specific population in one contiguous region keeps the function readable. |
| `ConfigExistsOnIntegration` inputs | `config.ProjectRoot` (absolute path already resolved by `SupervisorConfig`), `state.Config.IntegrationBranch` (same field already consumed at prompt.go:172). |
| `BootstrapInFlight` input | `state` (the in-memory state already passed into the function). |
| Error wrapping | Wrap with `fmt.Errorf("precommit config check: %w", err)`. Short prefix so the supervisor log line stays scannable; the `%w` preserves the underlying git error for diagnostic log capture. Only the `ConfigExistsOnIntegration` path errors — `BootstrapInFlight` is error-free by construction (§2.4). |
| Existing non-architect path | All pre-architect blocks in the function stay unchanged. The one at prompt.go:212 (ParentTaskContexts) now sits inside the architect-specific region it already gates on, so no refactor is required there. |

### 3.3 `buildPromptWithContext` adjustment (`prompt.go:32`)

```go
    data, err := buildTaskRoleContextData(task, state, config, resolver)
    if err != nil {
        return "", err
    }

    context, err := prompts.BuildRoleContext(config.Role, sections, data)
```

Single new two-line error guard between the call and `BuildRoleContext`. No wrapping at this layer — the helper already wraps, and the supervisor wraps again at its own layer. Double-wrapping would make log lines noisy without adding diagnostic value.

### 3.4 Orchestrator path

`buildOrchestratorPromptContext` (`prompt.go:66`) does not call `buildTaskRoleContextData` — it constructs `RoleContextData` directly and never sets the two new fields. Orchestrators are not architects; the fields stay at their `false` zero value. No code change required in that function.

### 3.5 Test-surface ripple

Every caller of `buildTaskRoleContextData` in `prompt_test.go` (20 call sites per the grep inventory) must absorb the new `(data, err)` return. The code-planning child task owns the mechanical rewrite; this plan fixes the boundary: callers must propagate the error via `t.Fatalf` for happy-path tests and use a dedicated test helper for the error-path case (§5.5). The helper should handle nil responses correctly and test the population path rather than the error-wrapping function itself.

## 4. Error Propagation — Helper Failure → BLOCKED Outcome

### 4.1 Flow

```
precommit.ConfigExistsOnIntegration  (git plumbing error)
        ↓ err
buildTaskRoleContextData             (returns err wrapped "precommit config check: ...")
        ↓ err
buildPromptWithContext               (returns err unwrapped — already descriptive)
        ↓ err
doerStrategy.BuildPrompt             (returns err unchanged — interface signature is already (string, error))
        ↓ err
supervisor loop (supervisor.go:817)  (current: wraps as "failed to build prompt: %w" and returns the entire supervisor error)
        ↓ detect + block
blockTaskFromSupervisor(...)         (marks task BLOCKED, releases lease, writes history)
```

### 4.2 Supervisor-side change (`supervisor.go:817-820`)

Current code:

```go
prompt, err := strategy.BuildPrompt(stateBefore, config, taskID)
if err != nil {
    return fmt.Errorf("failed to build prompt: %w", err)
}
```

Modified:

```go
prompt, err := strategy.BuildPrompt(stateBefore, config, taskID)
if err != nil {
    if claimedTaskID != "" {
        reason := fmt.Sprintf("prompt context build failed: %v", err)
        blockTaskFromSupervisor(bb, config.ProjectRoot, claimedTaskID, config.AgentID, reason)
        GetLogger().Warn("Task blocked due to prompt-context build failure",
            "agent_id", config.AgentID,
            "task_id", claimedTaskID,
            "error", err)
        return nil
    }
    return fmt.Errorf("failed to build prompt: %w", err)
}
```

| Aspect | Spec |
|--------|------|
| When do we block? | Only when a task is actually claimed (`claimedTaskID != ""`). If the supervisor failed to build a prompt for something non-task-scoped (e.g. orchestrator prompt, which goes through a different code path — see §3.4 — but leaving the guard defensive), fall through to the old error return so the supervisor surfaces the failure. |
| What reason do we record? | `"prompt context build failed: %v"` — includes the wrapped chain, which contains `"precommit config check: …"` when our helper caused it. Arbitrary other prompt-build failures (template parse error etc.) use the same reason phrasing, which is correct: a prompt that cannot be built blocks the task regardless of sub-cause. |
| Return `nil` or the error? | `nil`. Blocking the task IS the recovery — the supervisor has handled the failure. Returning the error would bubble up to the outer loop and trigger crash-restart logic, which is wrong: the task is now BLOCKED, so restart is pointless and would race with the BLOCKED state. |
| `blockTaskFromSupervisor` side effects (already existing) | Transitions task to BLOCKED via `TransitionWith(models.TaskStatusBlocked, ...)`; clears `AssignedTo`, `LeaseExpires`, `ReviewingBy`, `ReviewLeaseExpires`; appends a `TaskEventBlocked` history entry with `Reason` set. Default `BlockedQuestions` array (two generic questions about spec clarity / environment) is written — acceptable; this plan does not specialize the questions because the supervisor-side error site cannot know whether the root cause was a git issue, a template issue, or something else without pattern-matching the error, which is brittle. |
| Why not return a typed sentinel error and only block on that? | Rejected: it would require every non-helper BuildPrompt error source (template, resolver, pipeline YAML) to also be classified. The property we care about — "prompt could not be built for this claimed task" — is uniform across causes. Blocking uniformly is simpler and correct. The reason string preserves the sub-cause for diagnosis. |

### 4.3 Why not raise the error through to exit-code handling?

The existing exit-code dispatcher at `supervisor.go:841` handles exits from an agent that **was executed**. The agent never runs when `BuildPrompt` fails (control never reaches `executeAgent`). So the exit-code machinery cannot translate this failure; we must mark the task BLOCKED at the BuildPrompt site itself. That is exactly what `blockTaskFromSupervisor` was built for (its two existing call sites at L790, L917 both handle pre-exec failures — worktree-check crashes and post-exec restart loops). This is a natural third caller in that family.

### 4.4 Observable outcomes (contract)

| Outcome | Observable state |
|---------|------------------|
| Helper returns `(true, nil)` | Task prompt contains `PreCommitConfigExists=true`; architect omits bootstrap entry. Task status unchanged. |
| Helper returns `(false, nil)` and scan finds no in-flight | `PreCommitConfigExists=false`, `PreCommitBootstrapInFlight=false`. Architect MAY emit bootstrap. Task status unchanged. |
| Helper returns `(false, nil)` and scan finds in-flight | `PreCommitConfigExists=false`, `PreCommitBootstrapInFlight=true`. Architect omits (duplicate would be dedup'd by proceed.go anyway — belt-and-braces). Task status unchanged. |
| Helper returns `(_, err)` | Architect agent is **not** executed. Task transitions to BLOCKED with `BlockedReason` starting `"prompt context build failed: precommit config check: …"`. Orchestrator sees BLOCKED on next poll; downstream gating is unchanged (dep resolution already treats BLOCKED as unsatisfied per `checkDependencies`, `task.go:522`). |

The fourth row is the explicit **not silent omission, not opaque crash** outcome the goal spec requires.

## 6. Cross-cutting Concerns

### 6.1 Dependency on architecture-1

The `Kind` field on `Task` is a prerequisite (`BootstrapInFlight` reads `task.Kind`). Architecture-1 is MERGED at the time of this plan; the field is already on `main` integration. If a future rebase inverted the merge order, the code-planner must detect the missing field at build time and surface BLOCKED before code lands. This is mechanical — `go build` would fail — so no extra plumbing needed. Called out here only so the code-planning task's `depends_on` array correctly declares dependency on architecture-1's outputs.

### 6.2 Concurrency / TOCTOU

The plan-time check is a best-effort early filter. The authoritative guarantee lives in `proceed.go`'s dedup (architecture-1 §3). This plan does not attempt to lock, snapshot, or otherwise coordinate between the prompt-time read and the eventual proceed-time write; any race there is resolved by the authoritative layer.

### 6.3 Observability

- Helper failures surface via the supervisor log line (`"Task blocked due to prompt-context build failure"`) and the task's history (`TaskEventBlocked` with a descriptive reason). No new log stream.
- Successful reads produce no output — standard Go pattern for pure detection helpers. If diagnostics are needed later, a single structured log line in the helper is trivial to add.

### 6.4 Migration / backward compat

- Adding two `bool` fields to `RoleContextData` is purely additive (zero-value for every existing caller).
- Template blocks that consume these fields are emitted by a sibling task; until that task lands, the fields are populated but not rendered. No user-visible change from this plan alone.
- Changing `buildTaskRoleContextData`'s signature from `*RoleContextData` to `(*RoleContextData, error)` is a compile-time-visible break for test files; the code-planning child is responsible for the mechanical rewrite. No on-disk state or protocol change.

### 6.5 Performance

Both helpers run once per architect prompt build — that is, once per claim of an architect task. The git plumbing is a single `cat-file -e` (microseconds). The state scan is O(n) over an already-loaded slice. Net cost is lost in the noise compared to the template-rendering pipeline already executing in `buildPromptWithContext`.

### 6.6 Error domain ownership

- `precommit` package owns: git plumbing errors, input-validation errors (empty `projectRoot` / empty branch).
- `agent.buildTaskRoleContextData` owns: wrapping those errors with the prefix `"precommit config check: %w"` and threading through.
- `agent.supervisor` owns: translation from wrapped error to BLOCKED state via `blockTaskFromSupervisor`.

No owner overlaps. This is the architecturally clean three-layer split.
