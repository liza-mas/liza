# Architecture Plan: Acceptance Coverage And Artifact Reference Documentation

Status: draft

## Goal

Define the acceptance, regression, and documentation planning boundary that proves candidate-tree artifact reference protection behaves correctly across protected fields, merge paths, invalid object replacements, diagnostics, races, and durable specs.

## Context

The sibling architecture plans split implementation into collector/provenance (`architecture-1`), the CAS pre-update hook boundary (`architecture-2`), and the candidate-tree artifact guard (`architecture-3`). This plan does not add another production component. It defines how downstream code-planning should close the feature by adding end-to-end acceptance coverage and updating durable invariant/protocol/schema documentation after those implementation plans are available.

The current system already has a post-merge artifact validation backstop in `MergeWorktree`: `performCASMerge` advances the integration ref, `SyncMergedFiles` updates the working tree, and `statevalidate.ValidateArtifactRefs` can roll back when state still references a deleted artifact. The goal spec requires the new primary guard to reject invalid candidate trees before `UpdateRef`, while preserving that backstop. Acceptance coverage must therefore assert both the new pre-update behavior and the retained post-update rollback behavior.

### Constraints

- Scope is planning only. No production code, tests, or durable docs are changed by this architecture task.
- Acceptance coverage must exercise behavior observable at the `wt-merge` and validator boundaries, not implementation details below the interfaces defined by sibling plans.
- `performCASMerge` must remain artifact-policy agnostic; acceptance tests for artifact policy should go through `MergeWorktree` or the guard-facing validator, not by adding artifact assertions inside CAS tests.
- The existing post-merge `ValidateArtifactRefs` backstop remains documented and tested.
- `.pre-commit-config.yaml` exists at worktree `HEAD`; no `bootstrap-precommit` output entry is emitted.
- Project guardrail G1.2 applies because this feature changes integration protection. The coverage and documentation plan must preserve the integration-ref, rollback, state-validation, and CAS concurrency invariants.

## Components

### Acceptance Matrix Planner (`specs/plans` downstream task)

**Responsibility:** Convert every acceptance criterion and non-functional requirement in the goal spec into concrete test obligations with owners, test level, and expected diagnostics.

**Boundaries:**
- Exposes: a code plan for acceptance/regression tests and a requirement-to-test matrix.
- Depends on: the goal spec, sibling architecture plans, existing `wt_merge` integration-style test helpers, statevalidate collector/validator plans, and Git wrapper test patterns.

**Key decisions:**
- Treat the matrix as the single source for downstream coverage so field coverage, merge-path coverage, race coverage, and diagnostics cannot drift independently.
- Keep this as a planning component instead of a production package; code planners and coders can implement the matrix using existing Go tests and helper functions.

### Merge Acceptance Harness (`internal/ops` tests)

**Responsibility:** Exercise `MergeWorktree` end to end enough to prove candidate-tree rejection happens before integration ref advancement and post-merge validation still runs after successful updates.

**Boundaries:**
- Exposes: behavior through `MergeWorktree(projectRoot, taskID, agentID)` and observable Git/state outcomes.
- Depends on: test repositories, `.liza/state.yaml` fixtures created through existing test helpers, approved task state, and the production `performCASMerge` hook wiring from sibling plans.

**Key decisions:**
- Reuse and extend the current `TestMergeWorktree_RejectsDeletingReferencedArtifact` style rather than creating a parallel harness.
- Assert pre-update protection by comparing the integration ref before and after a rejected merge; a rollback after ref advancement is not sufficient evidence for AC-001-1 through AC-001-8.
- Cover true merge and fast-forward paths separately because `performCASMerge` validates different candidate treeishes for each path.

### Boundary Regression Tests (`internal/statevalidate` and `internal/git` tests)

**Responsibility:** Provide focused regression coverage for invalid refs, Git object mode classification, deterministic diagnostics, and owner provenance where end-to-end tests would be too expensive or ambiguous.

**Boundaries:**
- Exposes: package tests against the collector, candidate validator, and Git tree path query planned by sibling tasks.
- Depends on: collector output ordering, owner metadata, mode query results, and structured error details.

**Key decisions:**
- Use boundary tests for exhaustive object mode and invalid-ref matrices, then sample those cases through `MergeWorktree` to prove wiring.
- Assert stable strings or structured safe details only where sibling plans define deterministic diagnostics; avoid tests that rely on Go map iteration.

### Documentation Impact Mapper (`INVARIANTS.md`, `specs/protocols`, `specs/architecture`)

**Responsibility:** Identify durable documentation updates required by the new primary pre-update guard and the clarified artifact-ref validity rules.

**Boundaries:**
- Exposes: a documentation code plan covering invariant, protocol, and schema updates.
- Depends on: current docs for post-merge rollback, scalar artifact refs, and output/task artifact fields.

**Key decisions:**
- Update existing sections rather than adding a separate standalone doc, because the feature changes existing integration and state-validation guarantees.
- Document that rollback remains a backstop, while candidate-tree validation is the primary guard before integration ref advancement.

## Interfaces

### Acceptance Matrix Planner -> Merge Acceptance Harness

**Contract:** The matrix names the state artifact owner, candidate mutation, merge path, expected ref/state outcome, and diagnostic assertion for each end-to-end test.

**Direction:** Code-planning produces test cases; ops tests implement them through `MergeWorktree`.

**Invariants:** Every rejected candidate assertion checks that the integration ref did not advance. Every successful candidate assertion checks that post-merge validation is still reachable.

### Acceptance Matrix Planner -> Boundary Regression Tests

**Contract:** The matrix assigns exhaustive invalid-ref, object-mode, owner ordering, and diagnostic cases to package-level tests when end-to-end repetition would add cost without more confidence.

**Direction:** Code-planning maps requirements to statevalidate/git tests; those tests verify the reusable boundaries used by `MergeWorktree`.

**Invariants:** Boundary tests must still use public or package-supported interfaces from sibling plans, not duplicate artifact traversal or Git mode parsing.

### Documentation Impact Mapper -> Durable Specs

**Contract:** Documentation updates must describe the protected artifact fields, pre-update candidate-tree guard, retained post-merge backstop, rejected object modes, and diagnostic expectations.

**Direction:** The documentation plan points to existing docs and sections; implementation edits those docs after the production/test behavior is settled.

**Invariants:** Docs stay stack-agnostic and do not hardcode Liza development commands as user-project defaults.

## Cross-Cutting Concerns

| Concern | Approach |
|---------|----------|
| Error handling | Tests assert fail-closed behavior for invalid refs, candidate validation failures, state reread failures, and integration staleness read failures. |
| Observability | Diagnostics assertions require invalid path plus deterministic owner provenance, with task ID and artifact field where applicable. |
| Configuration | No new configuration. Tests use existing integration branch and project-root setup helpers. |
| Concurrency | CAS retry tests remain at the `performCASMerge` boundary; artifact acceptance tests assert ref-stability when hook failures are stale or current. |
| Security | Test refs are synthetic repo-local paths. Credential files are not read. Docs preserve the rule that durable artifacts must be direct regular files, not symlink indirections. |
| Testing | Coverage is split between `internal/ops`, `internal/statevalidate`, and `internal/git` based on the boundary that owns the behavior. |
| Documentation | Update existing invariant/protocol/schema docs so durable memory matches runtime behavior. |

## Structural Decisions

### Decision 1: Put End-To-End Acceptance At `MergeWorktree`

Acceptance tests that prove integration ref protection should call `MergeWorktree` because it is the public operation that builds the artifact guard hook, calls `performCASMerge`, syncs files, performs post-merge validation, and transitions task state.

**Rationale:** The goal is about `wt-merge` rejecting candidates before integration ref advancement. Testing lower than `MergeWorktree` would miss wiring and state outcome regressions.

### Decision 2: Use Boundary Tests For Exhaustive Field And Object Matrices

The full matrix includes many protected fields and invalid object modes. Exhaustive combinations should live in statevalidate/git boundary tests, with representative end-to-end tests proving the wiring.

**Rationale:** This keeps acceptance coverage complete without making every test pay the cost of a full Git worktree and blackboard lifecycle.

### Decision 3: Assert Pre-Update Rejection By Ref Equality

Rejected candidate tests must capture integration HEAD before `MergeWorktree` and assert it is unchanged afterward.

**Rationale:** The existing post-merge rollback path can also end with the old ref. The observable difference required by NFR-000-1 is that the ref never advances for candidate-tree guard failures.

### Decision 4: Keep Documentation Updates In Existing Durable Specs

The docs work belongs in `INVARIANTS.md`, `specs/protocols/worktree-management.md`, and `specs/architecture/blackboard-schema.md`.

**Rationale:** Those docs already define integration rollback, worktree merge protocol, and artifact-ref schema semantics. Updating them avoids a second source of truth.

## Validation And Test Strategy

### Test Targets

- `internal/ops/wt_merge_test.go`: end-to-end `MergeWorktree` acceptance tests for protected artifact fields, true merge, fast-forward, ref advancement, hook race behavior, CAS retry outcomes, no-op behavior, and retained post-merge backstop.
- `internal/statevalidate/*_test.go`: collector/validator tests for invalid refs, owner provenance, deterministic diagnostics, and candidate validator handling of missing/non-regular paths.
- `internal/git/*_test.go`: Git tree path query tests for regular file, executable file, directory, submodule, symlink, missing path, and unknown/non-regular modes where the wrapper can simulate or observe them.

### Acceptance Criteria Coverage

| Acceptance Criterion | Concrete coverage plan |
|----------------------|------------------------|
| AC-001-1 | `MergeWorktree` true-merge test where task commit deletes another task's `arch_ref`; assert error before integration ref advances and diagnostic names path/task/field. |
| AC-001-2 | Table-driven true-merge tests for task `plan_ref`, `spec_ref`, and `epic_ref` deletion; assert ref unchanged and owner-aware diagnostic for each field. |
| AC-001-3 | Table-driven true-merge tests for `output[].arch_ref`, `output[].plan_ref`, `output[].spec_ref`, and `output[].epic_ref` deletion; assert output index appears in deterministic diagnostics. |
| AC-001-4 | Fast-forward deletion test for a protected artifact; assert `expectedCommit` candidate is rejected before `UpdateRef` and integration ref stays at pre-merge HEAD. |
| AC-001-5 | Goal `spec_ref` deletion/removal test; assert goal-level owner diagnostic and pre-update ref preservation. |
| AC-001-6 | Rename regression using `git mv` or equivalent; assert old referenced path is missing in candidate tree, not silently treated as preserved by Git rename detection. |
| AC-001-7 | Boundary mode matrix for directory, submodule, symlink `120000`, and other non-regular modes, plus at least one `MergeWorktree` replacement test proving invalid-mode rejection before ref advancement. |
| AC-001-8 | Invalid-ref tests for semicolon-joined refs, empty-after-fragment, traversal, and unsafe absolute refs; include one `MergeWorktree` invalid-ref rejection with actionable diagnostic. |
| AC-001-9 | Hook freshness test where first snapshot protects a failing path, second snapshot no longer protects it, and the same candidate validates; assert hook invocation succeeds. |
| AC-001-10 | Hook freshness test forcing second state read failure; assert returned error preserves candidate failure and freshness failure. |
| AC-001-11 | CAS test where hook fails but integration HEAD changes after candidate computation; assert stale hook error is discarded and the CAS loop retries. |
| AC-001-12 | CAS test where hook fails and integration HEAD reread fails; assert composite error preserves hook failure and staleness read failure. |
| AC-001-13 | CAS conflict test where hook passes before `UpdateRef` conflict; assert retry recomputes candidate and re-runs hook. |
| AC-001-14 | Already-merged no-op test; assert `performCASMerge` returns without invoking the hook. |
| AC-001-15 | Post-merge backstop regression where ref update succeeds but later `ValidateArtifactRefs` fails; assert rollback/`INTEGRATION_FAILED` path remains available. |
| AC-001-16 | Diagnostic assertions across candidate validation failures require invalid path and at least one deterministic owner, including task ID and field when applicable. |

|-------------|------------------------|

| NFR-000-2 | CAS retry tests from `architecture-2` remain and are extended to include hook failure/pass cases without changing retry ownership. |
| NFR-000-3 | Diagnostic tests assert stable path, cause, mode when present, and owner provenance ordering. |
| NFR-000-4 | Test structure keeps artifact assertions outside `performCASMerge` internals; docs state `performCASMerge` receives only an opaque hook. |
