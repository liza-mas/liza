# Architecture Plan: performCASMerge Pre-Update Hook Boundary

Status: draft

## Goal

Define the narrow `performCASMerge` pre-update hook boundary so candidate tree validation can run before integration ref advancement while preserving existing CAS retry behavior.

## Context

`MergeWorktree` currently delegates integration ref advancement to `performCASMerge`, then runs post-merge `statevalidate.ValidateArtifactRefs` as a rollback backstop. The goal spec adds a pre-update candidate-tree guard, but requires `performCASMerge` to stay artifact-policy agnostic. This plan covers only the CAS merge hook boundary: hook interface, candidate treeish selection, no-op behavior, hook failure staleness handling, and retry semantics.

### Constraints

- `performCASMerge` must not import or depend on blackboard state, artifact-ref collection, artifact validation policy, or provenance formatting.
- The pre-update hook contract is opaque to `performCASMerge`: it receives only the candidate treeish and returns an error.
- The hook must run after the current CAS attempt computes its candidate and before that attempt calls `UpdateRef`.
- The already-merged path remains a no-op and must not run the hook.
- Existing post-merge `ValidateArtifactRefs` remains in `MergeWorktree` as the backstop after successful ref update.
- Existing bounded CAS retry semantics from ADR-0022 remain owned by `performCASMerge`.
- `.pre-commit-config.yaml` already exists at worktree `HEAD`; no bootstrap-precommit output entry is emitted.

## Components

### CAS Merge Coordinator (`internal/ops/wt_merge.go`)

**Responsibility:** Own working-tree-less merge candidate computation, compare-and-swap ref advancement, and retry decisions for concurrent integration updates.

**Boundaries:**
- Exposes: `performCASMerge` behavior used by `MergeWorktree`; no public package API is required.
- Depends on: `internal/git.Git` operations for ancestry checks, merge-tree, commit-tree, ref reads, and CAS `UpdateRef`.

**Key decisions:**
- Add an optional pre-update hook argument to `performCASMerge`: this keeps callers without a guard unaffected and avoids embedding artifact semantics in the CAS loop.
- Keep hook invocation inside the CAS attempt loop: every recomputed candidate is validated against the candidate treeish for that attempt.
- Route hook failures through a small CAS-staleness branch before returning: this preserves concurrency safety when a hook result was computed against stale integration HEAD.

### Pre-Update Hook Contract (`internal/ops/wt_merge.go`)

**Responsibility:** Represent an opaque validation callback over a Git treeish selected by `performCASMerge`.

**Boundaries:**
- Exposes: a function shape equivalent to `func(candidateTreeish string) error`.
- Depends on: no state model and no artifact-specific types.

**Key decisions:**
- The hook receives a treeish rather than a commit-only SHA: fast-forward paths can pass `expectedCommit`, and true merge paths can pass either a tree object or the merge commit object.
- The hook is optional and nil-safe: a nil hook preserves current `performCASMerge` behavior.
- Hook errors are returned unchanged when integration HEAD is unchanged, preserving downstream diagnostic ownership.

### Git Ref Operations (`internal/git`)

**Responsibility:** Provide the existing ref read and CAS update primitives used by `performCASMerge`.

**Boundaries:**
- Exposes: `GetCommitSHA`, `IsAncestor`, `MergeTree`, `CreateCommitFromTree`, and `UpdateRef`.
- Depends on: Git CLI execution through `gitenv`.

**Key decisions:**
- No new artifact-specific Git operation belongs in `performCASMerge`; candidate-tree inspection belongs to the hook implementation planned by other scopes.
- Staleness detection after hook failure reuses `GetCommitSHA(integrationRef)` so `performCASMerge` can compare the current integration HEAD to the attempt's `preMergeHEAD`.

## Interfaces

### `MergeWorktree` -> `performCASMerge`

**Contract:** `MergeWorktree` passes the integration ref, approved task commit, task ID, and optionally a pre-update hook. `performCASMerge` returns the existing merge outcome or an error.

**Direction:** `MergeWorktree` calls `performCASMerge`; `performCASMerge` owns retry and returns one final result.

**Invariants:** `MergeWorktree` must not advance the integration ref outside `performCASMerge`; post-merge artifact validation remains after a successful `performCASMerge` result.

### `performCASMerge` -> Pre-Update Hook

**Contract:** For each CAS attempt that has a candidate ref target, `performCASMerge` calls the hook once with the candidate treeish before `UpdateRef`. A nil hook is skipped.

**Direction:** `performCASMerge` calls the hook; the hook returns success or error.

**Invariants:**
- Already-merged no-op returns before hook invocation.
- Fast-forward candidate treeish is `expectedCommit`.
- True-merge candidate treeish is the candidate merge commit or candidate merge tree computed for that attempt.
- `performCASMerge` does not inspect hook error types for artifact meaning.

### `performCASMerge` -> Git Ref Operations

**Contract:** Each attempt reads integration HEAD, computes no-op/fast-forward/true-merge state, optionally runs the hook, then calls `UpdateRef` with the same `preMergeHEAD` used for candidate computation.

**Direction:** `performCASMerge` calls `internal/git`.

**Invariants:**
- `UpdateRef` CAS conflicts retry from a fresh integration HEAD.
- Hook failures trigger a fresh integration HEAD read before returning.
- If the fresh read differs from the attempt's `preMergeHEAD`, the hook error is stale and the attempt is retried.
- If the fresh read fails, the returned error preserves both the hook failure and the failed staleness check.

## Data Flow

```text
MergeWorktree
  -> resolve approved review_commit as expectedCommit
  -> performCASMerge(integrationRef, expectedCommit, taskID, optionalHook)
     -> read preMergeHEAD
     -> already-merged check: expectedCommit ancestor of preMergeHEAD
        -> return no-op outcome without hook
     -> fast-forward check: preMergeHEAD ancestor of expectedCommit
        -> optionalHook(expectedCommit)
        -> UpdateRef(integrationRef, expectedCommit, preMergeHEAD)
     -> true merge
        -> MergeTree(preMergeHEAD, expectedCommit)
        -> clean=false returns conflict outcome without hook
        -> CreateCommitFromTree(treeSHA, parents)
        -> optionalHook(candidate merge commit or tree)
        -> UpdateRef(integrationRef, mergeCommit, preMergeHEAD)
     -> on RefConflictError from UpdateRef: retry loop
     -> on hook error:
        -> re-read integrationRef
        -> changed: discard stale hook error and retry loop
        -> unchanged: return hook error
        -> read failure: return error preserving hook error and read failure
  -> SyncMergedFiles
  -> post-merge statevalidate.ValidateArtifactRefs backstop
  -> integration tests and final state transition
```

## Cross-Cutting Concerns

| Concern | Approach |
|---------|----------|
| Error handling | Hook failures are policy-owned errors unless `performCASMerge` proves the candidate was stale; staleness-read failures wrap and preserve the original hook failure. CAS conflicts remain `RefConflictError`-driven retries. |
| Observability | Keep existing CAS retry logging. Do not log artifact details in `performCASMerge`; hook implementations own diagnostics. |
| Configuration | None. The hook is caller-provided and nil-safe. No project-stack assumptions are introduced. |
| Concurrency | All retry decisions remain in `performCASMerge`; hook success does not bypass `UpdateRef` CAS. Hook failure staleness detection protects against returning errors for candidates that are no longer current. |
| Security | No credential files or secret-bearing state are read by `performCASMerge`; candidate validation policy is outside this boundary. |
| Testing | Add focused `internal/ops/wt_merge_test.go` coverage around hook invocation, treeish selection, no-op skip, hook-failure staleness, hook-failure staleness-read failure, and CAS conflict retry. |

## Structural Decisions

### Decision 1: Keep The Hook Contract Treeish-Only

`performCASMerge` should accept a callback equivalent to `func(candidateTreeish string) error`, not a richer interface containing task, state, artifact refs, or provenance.

**Rationale:** FR-001-19 and NFR-001-2 require `performCASMerge` to treat the hook as opaque. A treeish is the smallest boundary that lets artifact validation inspect the candidate Git tree while preserving separation from blackboard state.

### Decision 2: Invoke The Hook After Candidate Computation And Before CAS Update

Fast-forward attempts call the hook after `isFF` succeeds and before `UpdateRef(expectedCommit, preMergeHEAD)`. True-merge attempts call it after a clean merge candidate exists and before `UpdateRef(mergeCommit, preMergeHEAD)`.

**Rationale:** This satisfies FR-001-18, FR-001-21, and FR-001-22 while preventing validation against an incomplete candidate.

### Decision 3: Skip The Hook On Already-Merged And Merge-Conflict Paths

If `expectedCommit` is already an ancestor of integration HEAD, return the existing no-op outcome without hook execution. If `MergeTree` reports conflicts, return the existing conflict outcome without hook execution.

**Rationale:** The no-op path has no candidate ref update to protect and AC-001-14 explicitly requires no hook call. Merge conflicts do not advance the ref and remain handled by existing integration-failure flow.

### Decision 4: Treat Hook Failure As Potentially Stale Before Returning

On hook failure, `performCASMerge` re-reads `integrationRef`. If the ref changed from the attempt's `preMergeHEAD`, it discards the hook error and retries. If the ref is unchanged, it returns the hook error. If the ref cannot be read, it returns a composite error preserving the hook error and the staleness-read failure.

**Rationale:** This maps FR-001-23 through FR-001-26 and AC-001-11 through AC-001-12. It prevents stale candidate validation from blocking a merge after another integration update invalidated the attempted candidate.

### Decision 5: Preserve CAS Conflict Retry After Hook Success

If the hook passes but `UpdateRef` returns `git.RefConflictError`, the loop continues exactly as today. The next attempt re-reads integration HEAD, recomputes the candidate, and re-runs the hook for that new candidate.

**Rationale:** This maps FR-001-27 and AC-001-13 while preserving ADR-0022's bounded CAS concurrency model.

## Validation And Test Strategy

### Unit And Integration Test Targets

- `internal/ops/wt_merge_test.go`: package-level tests around `performCASMerge` and `MergeWorktree` flows using temporary Git repositories.
- Existing helper: `setupMergeTestRepo` for integration branch, worktree, approved task state, and review commit setup.
- Existing test hook: `mergeCASRetryTestHook` can continue to force CAS conflicts after integration HEAD reads; new pre-update hook tests should avoid blackboard/artifact policy coupling.

### Required Test Cases

| Requirement | Test strategy |
|-------------|---------------|
| FR-001-17 | Compile-time use of the new optional hook in `performCASMerge`; nil hook preserves existing tests. |
| FR-001-18 | Test that hook call count increments after candidate computation and before successful `UpdateRef`; verify `UpdateRef` does not advance when hook returns an unchanged-head error. |
| FR-001-19 | Keep tests' hook as a plain closure over local counters and Git operations; no state or artifact types enter `performCASMerge`. |
| FR-001-20 / AC-001-14 | Build an already-merged scenario and assert `performCASMerge` returns success with zero hook calls. |
| FR-001-21 | Fast-forward test asserts the hook receives `expectedCommit` and integration HEAD advances only after hook success. |
| FR-001-22 | True-merge test asserts the hook receives a treeish whose tree contains both parents' non-conflicting changes before `UpdateRef`. |
| FR-001-23 / FR-001-25 | Hook returns sentinel error while integration HEAD is unchanged; assert returned error preserves the sentinel and ref is not advanced. |
| FR-001-24 / AC-001-11 | Hook advances integration to a competing commit, then returns sentinel error; assert `performCASMerge` retries and final integration contains both competing and task commits. |
| FR-001-26 / AC-001-12 | Hook makes the integration ref unreadable before returning sentinel error; assert returned error contains both the sentinel and staleness-read failure. |
| FR-001-27 / AC-001-13 | Extend the existing deterministic CAS retry scenario so a passing pre-update hook is invoked once per recomputed candidate and final integration contains both competing and task commits. |

### Non-Regression Checks

- Existing post-merge `ValidateArtifactRefs` test remains valid until the artifact guard hookup scope changes it from rollback-primary to pre-update-primary behavior.
- Existing merge conflict, integration test failure, rollback, missing worktree, and CAS retry tests continue to pass with nil hook behavior.
- `go test ./internal/ops ./internal/git ./internal/statevalidate` should exercise the directly affected packages once implementation exists.

## Decomposition

Each scope becomes a code-planning child task.

### Scope 1: CAS Pre-Update Hook Boundary

**Component(s):** `internal/ops/wt_merge.go`, `internal/ops/wt_merge_test.go`

**Boundary:** Plan the code changes that add the optional `performCASMerge` pre-update hook, choose candidate treeish values for fast-forward and true-merge attempts, preserve no-op behavior, implement hook-failure staleness handling, and preserve CAS retry semantics. Out of scope: artifact-ref collection, candidate artifact validation policy, state re-read freshness inside the artifact guard, and blackboard coupling.

**Done when:** A code plan is ready for implementation that, when implemented, makes `performCASMerge` accept an optional `func(candidateTreeish string) error` hook, skip it for already-merged no-op returns, pass `expectedCommit` for fast-forward candidates, pass the candidate merge treeish for true merges before `UpdateRef`, retry when hook failure is stale because integration HEAD changed, preserve hook and staleness-read errors when HEAD cannot be re-read, and re-run the hook after CAS conflicts; the plan includes tests for FR-001-17 through FR-001-27 and AC-001-11 through AC-001-14.

**Depends on:** None.
