# Architecture Plan: Candidate Tree Artifact Guard

Status: draft

## Goal

Compose the artifact-ref collector and CAS pre-update hook work into a pre-ref-advance candidate-tree guard that validates protected artifact refs with fresh state snapshots while preserving the post-merge `ValidateArtifactRefs` backstop.

## Context

`MergeWorktree` currently advances the integration ref through `performCASMerge`, syncs affected files into the project working tree, re-reads state, and then runs `statevalidate.ValidateArtifactRefs`. That post-merge check can roll back a bad merge, but the integration ref has already advanced before artifact-reference failures are discovered.

This plan covers the final guard layer for `specs/goals/20260520-artifact-ref-protection.md`. Parent plan `architecture-1` owns artifact-ref collection, repo-relative normalization, invalid-ref handling, and deterministic owner provenance. Parent plan `architecture-2` owns the opaque `performCASMerge` pre-update hook contract and CAS retry behavior. This plan defines the candidate Git tree validation policy, `MergeWorktree` hook wiring, fresh-state lifecycle for every hook invocation, second-snapshot failure confirmation, fail-closed state reread errors, and retention of the existing post-merge validator.

### Constraints

- `performCASMerge` must stay artifact-policy agnostic. It receives only an opaque pre-update hook equivalent to `func(candidateTreeish string) error`.
- Candidate checks must happen before `UpdateRef` on normal fast-forward and true-merge paths.
- The artifact guard must read the latest available blackboard state inside every hook invocation and collect protected refs from that snapshot.
- Candidate validation must use Git tree state, not filesystem state, and must accept only modes `100644` and `100755`.
- Missing paths, directories, submodules, symlinks with mode `120000`, and any other non-regular object mode must fail closed with deterministic owner-aware diagnostics.
- Candidate validation failure must trigger exactly one fresh state reread and revalidation against the same candidate treeish before returning an artifact error.
- If the second snapshot no longer protects the previously failing path and the candidate validates against that second snapshot, the hook returns success for that invocation.
- If state cannot be reread for failure confirmation, the hook fails closed and preserves both the candidate-tree failure and the state freshness failure.
- Existing post-merge `ValidateArtifactRefs` must remain after successful ref updates.
- `.pre-commit-config.yaml` exists at worktree `HEAD`; no `bootstrap-precommit` output entry is emitted.
- Project guardrail G1.2 applies because this work touches integration, concurrency, and artifact-reference protection invariants. The plan preserves CAS ownership in `performCASMerge`, keeps blackboard mutations behind existing ops paths, and retains rollback validation.

## Components

### Candidate Tree Artifact Validator (`internal/statevalidate` with `internal/git`)

**Responsibility:** Validate collected protected artifact refs against one candidate Git treeish and return stable diagnostics for missing or non-regular paths.

**Boundaries:**
- Exposes: a guard-facing validation boundary that accepts a candidate treeish plus collected artifact refs, or an equivalent API at the same boundary.
- Depends on: the collector and provenance model from `architecture-1`, and a narrow Git tree lookup operation.
- Does not depend on: blackboard state loading, `MergeWorktree` lifecycle, CAS retry state, or task status transitions.

**Key decisions:**
- Keep artifact validation policy in `statevalidate`, because this package owns artifact-ref meaning and diagnostics.
- Keep raw Git object lookup in `internal/git`, because mode extraction is a Git concern and can be reused without artifact semantics.
- Query the candidate treeish with `git ls-tree <treeish> -- <path>` or an equivalent wrapper that distinguishes missing path from present mode.
- Accept only modes `100644` and `100755`; reject `120000`, tree modes, submodule modes, and any unknown or non-regular mode.
- Deduplicate Git lookups by normalized path where practical, but keep deterministic owners for diagnostics on a failing path.

### Git Tree Path Query (`internal/git`)

**Responsibility:** Provide a narrow query over a treeish/path pair that reports whether the path exists in that tree and, when present, the Git object mode.

**Boundaries:**
- Exposes: a small query such as `TreeEntryMode(treeish, path)` or equivalent.
- Depends on: existing Git command execution helpers and repo-root context.
- Does not depend on: blackboard state, artifact-ref owners, or validation policy.

**Key decisions:**
- The query returns a present/missing distinction instead of encoding missing as a mode.
- Mode strings remain Git modes at the query boundary so policy stays in the validator.
- The command uses `--` before the path, and callers pass only collector-normalized repo-relative paths.

### Artifact Guard Hook (`internal/ops/wt_merge.go`)

**Responsibility:** Bridge `MergeWorktree` to candidate validation by constructing the pre-update hook passed into `performCASMerge`.

**Boundaries:**
- Exposes: no public CLI or package API beyond `MergeWorktree` behavior.
- Depends on: blackboard reads, `statevalidate.CollectArtifactRefs`, candidate-tree validation, project root context, and the `performCASMerge` hook boundary from `architecture-2`.
- Does not depend on: `performCASMerge` internals other than receiving one candidate treeish per hook invocation.

**Key decisions:**
- Construct the hook in `MergeWorktree`, not in `performCASMerge`, to satisfy FR-001-19 and NFR-001-2.
- Read state inside the hook on every invocation; do not capture refs before entering the CAS loop.
- Treat collector invalid-ref errors as candidate rejection, because invalid refs cannot be checked safely against the candidate tree.
- Hook success is scoped to one invocation. State changes after hook success remain covered by the post-merge validator.

### Failure Confirmation Loop (`internal/ops` orchestration over `statevalidate`)

**Responsibility:** Confirm candidate validation failures against one fresh state snapshot before returning an artifact error, while failing closed if freshness cannot be established.

**Boundaries:**
- Exposes: guard-internal orchestration, not a broad reusable subsystem.
- Depends on: the first candidate validation failure, a second blackboard read, a second collector call, and revalidation of the same candidate treeish.
- Does not depend on: integration ref staleness. Hook-error staleness remains owned by `performCASMerge` per `architecture-2`.

**Key decisions:**
- On first candidate failure, reread state once and revalidate the same candidate treeish.
- If second validation passes, return success; this covers the case where state no longer protects the first failing path and all currently protected refs are valid.
- If second validation still fails, return the second validation failure so diagnostics reflect current owner provenance.
- If the second state read fails, return a composite error that preserves the first candidate failure and reports the freshness read failure.

### Post-Merge Artifact Backstop (`internal/ops/wt_merge.go` and `internal/statevalidate`)

**Responsibility:** Continue validating full current state after successful ref update and rolling back if post-merge artifact validation fails.

**Boundaries:**
- Exposes: existing `ValidateArtifactRefs` behavior from `MergeWorktree` after `performCASMerge` and file sync.
- Depends on: a post-merge blackboard read, current `ValidateArtifactRefs`, and rollback behavior.

**Key decisions:**
- Do not remove or weaken the post-merge `ValidateArtifactRefs` call.
- Keep rollback behavior for races after hook success and for any future artifact-ref gaps outside the pre-update guard.

## Interfaces

### Artifact Guard Hook -> Blackboard State

**Contract:** Each hook invocation reads the latest available state snapshot before collecting protected refs. State read failure before validation rejects the candidate because the guard cannot establish the protected ref set.

**Direction:** The hook calls `bb.Read()` or equivalent. The blackboard does not know about candidate Git trees.

**Invariants:**
- No protected refs are cached across hook invocations.
- Every validation attempt uses refs from the snapshot read inside that hook invocation.
- State read failures in the guard are fail-closed.

### Artifact Guard Hook -> Artifact Ref Collector

**Contract:** The hook passes the fresh state snapshot and project root to the collector from `architecture-1`, receiving normalized repo-relative refs with deterministic owner provenance or a fail-closed invalid-ref error.

**Direction:** The hook calls `statevalidate`; the collector does not call `ops` or Git.

**Invariants:**
- Returned paths are safe Git tree paths.
- Invalid refs reject the candidate before ref advancement.
- Diagnostics include field, task ID when applicable, output index when applicable, and invalid value/path.

### Candidate Tree Artifact Validator -> Git Tree Path Query

**Contract:** For each protected normalized path, the validator asks Git whether that path exists in the candidate treeish and which object mode it has.

**Direction:** The validator calls `internal/git`; Git returns path presence plus mode and does not apply artifact policy.

**Invariants:**
- Missing is distinguishable from present-with-invalid-mode.
- Only modes `100644` and `100755` satisfy artifact liveness.
- Path values are collector-normalized repo-relative strings.

### MergeWorktree -> performCASMerge

**Contract:** `MergeWorktree` passes the artifact guard hook into `performCASMerge`; `performCASMerge` invokes the hook after computing each candidate treeish and before `UpdateRef`.

**Direction:** `MergeWorktree` assembles policy; `performCASMerge` owns candidate computation, integration-ref staleness checks, and CAS retries.

**Invariants:**
- Already-merged no-op paths skip the hook per `architecture-2`.
- Fast-forward attempts validate `expectedCommit` before `UpdateRef`.
- True-merge attempts validate the candidate merge treeish or merge commit tree before `UpdateRef`.
- Hook errors remain opaque to `performCASMerge`.
- Post-merge `ValidateArtifactRefs` remains after successful `performCASMerge`.

## Data Flow

```text
MergeWorktree
  -> read task and state for merge preconditions
  -> create artifact guard hook with project root, blackboard, and Git wrapper
  -> performCASMerge(..., artifactGuardHook)
     -> compute candidate treeish for the current CAS attempt
     -> artifactGuardHook(candidateTreeish)
        -> read latest state snapshot
        -> CollectArtifactRefs(snapshot, projectRoot)
        -> ValidateCandidateArtifactRefs(candidateTreeish, refs)
           -> for each normalized path, git ls-tree candidateTreeish -- path
           -> accept 100644 or 100755
           -> reject missing, directory, submodule, symlink 120000, or other non-regular mode
        -> on candidate failure:
           -> reread state snapshot once
           -> recollect refs
           -> revalidate the same candidateTreeish
           -> return success only if the second snapshot validates
           -> fail closed if reread fails, preserving both errors
     -> UpdateRef only after hook success
     -> retry per CAS semantics when integration ref changes or UpdateRef conflicts
  -> SyncMergedFiles
  -> read current state
  -> statevalidate.ValidateArtifactRefs(currentState, projectRoot)
  -> integration tests and terminal task transition
```

## Cross-Cutting Concerns

| Concern | Approach |
|---------|----------|
| Error handling | Candidate validation errors include path, cause, mode when present, and owners. State read failures before initial validation or failure confirmation are fail-closed. Confirmation reread errors compose with the original candidate failure. |
| Observability | Error text and safe details are deterministic enough for tests: invalid path, cause, mode when present, and at least one owner including task ID and artifact field where applicable. No new logging is required inside `performCASMerge`. |
| Configuration | No new configuration. The guard uses the existing project root, blackboard path, integration branch, and Git wrapper already available to `MergeWorktree`. |
| Concurrency | `performCASMerge` continues to own integration-ref staleness checks and CAS retries. The artifact guard owns only blackboard state freshness for artifact refs. Hook success never bypasses `UpdateRef` CAS checks. |
| Security | The guard passes only collector-normalized repo-relative paths to Git. Unsafe refs fail during collection; the guard does not read credential files and does not follow filesystem symlinks. |
| Testing | Unit tests cover Git tree mode classification and candidate validator diagnostics. Ops tests cover fresh state per invocation, second-snapshot confirmation, fail-closed state read errors, fast-forward and true-merge pre-update rejection, CAS retry composition, and retained post-merge backstop behavior. |

## Structural Decisions

### Decision 1: Keep Artifact Policy Out Of `performCASMerge`

The guard is built by `MergeWorktree` and passed as the opaque hook planned by `architecture-2`.

**Rationale:** This satisfies FR-001-19, NFR-000-4, and NFR-001-2. `performCASMerge` keeps CAS and staleness ownership without importing statevalidate or blackboard semantics.

### Decision 2: Validate Git Tree Modes Before Ref Advancement

Candidate validation checks the candidate treeish through Git and accepts only regular-file modes `100644` and `100755`.

**Rationale:** The candidate may not exist in the working tree, and the required protection point is before `UpdateRef`. Git tree modes directly distinguish missing paths, directories, submodules, symlinks, and regular files.

### Decision 3: Read State Inside Every Hook Invocation

The guard reads state after `performCASMerge` computes the candidate treeish and invokes the hook.

**Rationale:** FR-001-12 requires the latest available state for each invocation. Capturing refs once before the CAS loop would validate retries against stale state.

### Decision 4: Confirm Candidate Failures With One Fresh Snapshot

On candidate validation failure, the hook rereads state, recollects refs, and revalidates the same candidate before returning an artifact error.

**Rationale:** FR-001-14 and FR-001-15 prevent stale artifact failures when current state no longer protects the first failing path, while still requiring the candidate to validate against the latest confirmed snapshot.

### Decision 5: Fail Closed When Freshness Cannot Be Verified

If the second state read fails, the hook returns a composite error preserving the candidate-tree failure and reporting the failed freshness check.

**Rationale:** FR-001-16 requires the merge to stop when the guard cannot prove the first artifact failure is stale.

### Decision 6: Retain Post-Merge Validation

The existing post-merge `ValidateArtifactRefs` call remains after successful `performCASMerge`.

**Rationale:** FR-001-13 and FR-001-28 require state changes after hook success to remain covered. The pre-update guard is the primary protection for candidate-invalidating commits, not the only protection.
