# Architecture Plan: Master Planning Acceptance, Documentation, and Non-Migration Boundaries

Status: draft

## Goal

Define the cross-cutting validation and documentation plan that proves the master planning task pattern satisfies success criteria 1-8, is documented for users and maintainers, has an ADR trail, and does not introduce runtime migration for existing workspaces.

## Context

The parent architecture tasks divide the feature across topology, INITIAL_PLANNING routing, master prompt sections, and typed decomposition metadata. This plan covers the remaining acceptance layer: broad scenario tests that compose those domains, documentation updates that explain the new topology and master task responsibilities, ADR treatment, and explicit non-migration boundaries for frozen workspaces.

This task does not implement behavior. It assigns downstream code-planning work for tests and docs after the domain-specific code-planning tasks have produced their implementation plans.

## Components

### Acceptance Scenario Suite (`internal/integration/`, `internal/ops/`, `cmd/liza/`)

**Responsibility:** Prove the feature composes end to end across pipeline config validation, initialization, status rendering, master review quorum, auto decomposition, artifact propagation, and Case A bypass.

**Boundaries:**
- Exposes: regression tests and validation commands that exercise success criteria 1-8.
- Depends on: topology from `architecture-1`, wake data and template behavior from `architecture-2-a` and `architecture-2-b`, master prompt behavior from `architecture-3-b`, and output-entry manifest validation/propagation from `architecture-4`.

**Key decisions:**
- Keep unit and focused package tests in the domain scopes; this scope adds composition tests that would fail if individually-correct domains do not interoperate.
- Reuse existing integration patterns in `e2e_workflow_test.go`, `full_sprint_test.go`, and `proceed_test.go` instead of adding a separate harness.
- Cover both `commands.InitCommandWithConfig`/state-level flows and CLI JSON surfaces where the user-visible success criteria mention `liza init --spec`, `liza status`, or `liza validate --json`.
- Treat missing-master legacy/frozen behavior as a compatibility scenario, not as a migration.

### Documentation Surface (`README.md`, `support-docs/`, `specs/architecture/`, `specs/build/`)

**Responsibility:** Update durable user and maintainer documentation for master planning tasks, entry-point routing, role responsibilities, state machines, output-entry schema, and frozen pipeline boundaries.

**Boundaries:**
- Exposes: user-facing quick-start and flow descriptions, maintainer architecture docs, role docs, state/schema docs, and pipeline configuration docs.
- Depends on: the goal spec and parent architecture plans for exact terms and propagation rules.

**Key decisions:**

- Keep docs explicit that `general-objective`, `functional-spec`, `detailed-spec`, and `technical-spec` still name specialized entry points, while INITIAL_PLANNING routes fan-out or uncertain work to the mapped master role-pair.
- Document typed decomposition metadata as an output-entry/task-level schema extension and explain that scheduling still uses `depends_on` and `task_depends_on`.
- Document no runtime migration for existing frozen workspaces; users must run a new `liza init` to pick up the new embedded topology.

## Interfaces

### Domain Implementations -> Acceptance Scenario Suite

**Contract:** Domain scopes provide pipeline topology, route data, prompt sections, and output-entry validation/propagation. Acceptance tests exercise the composed behavior without duplicating domain unit tests.
**Direction:** Acceptance tests initialize or construct workspaces, drive state transitions, and assert resulting tasks, refs, statuses, prompts, and validation output.
**Invariants:** Tests must fail when a success criterion regresses, even if lower-level package tests still pass.

### Acceptance Scenario Suite -> Liza CLI and Ops APIs

**Contract:** Scenario tests use existing command/ops surfaces such as init, status, validate, checkpoint/resume, submit verdict, merge, set-task-output, and execute transitions.
**Direction:** Tests drive the same surfaces used by agents and humans.
**Invariants:** State mutation remains CLI/ops-backed and lock-protected. No direct state-file edits are introduced outside existing test helpers.

### Documentation Surface -> Users and Maintainers

**Contract:** Docs describe what a user can observe and what a maintainer must preserve: one-task INITIAL_PLANNING, master quorum, master output contract, typed decomposition metadata, Case A bypass, and frozen-workspace non-migration.
**Direction:** README and support docs guide use; architecture docs guide maintenance and future changes.
**Invariants:** Docs must not imply existing workspaces automatically receive new role-pairs or transitions.

### ADR Trail -> Future Architecture Work

**Contract:** The ADR states the accepted decision, consequences, alternatives, and relationship to existing ADRs.
**Direction:** Future work reads ADRs to understand why fan-out planning now routes through reviewed master tasks.
**Invariants:** ADRs are historical records; they explain the decision and do not substitute for current schema and usage docs.

## Data Flow

Acceptance flow for simple entry-point work:

```text
liza init --spec <spec> --entry-point <entry>
  -> INITIAL_PLANNING route data exposes specialized simple target
  -> orchestrator creates exactly one specialized planning task
  -> liza status shows one created task and no master task
```

Acceptance flow for fan-out entry-point work:

```text
liza init --spec <spec> --entry-point <entry>
  -> INITIAL_PLANNING route data exposes mapped master target
  -> orchestrator creates exactly one master task
  -> master task reaches first approval -> partially-approved state
  -> master task reaches second approval -> approved state
  -> merge/checkpoint/resume runs auto decompose transition
  -> one specialized child per output[] entry with refs, deps, and decomposition metadata
```

Case A bypass flow:

```text
specialized architecture-pair task approved and merged
  -> architecture-to-code-plan
  -> code-planning-pair children
  -> no code-planning-main-pair task created
```

Non-migration flow:

```text
workspace initialized before new embedded topology
  -> frozen .liza/pipeline.yaml has no master mappings
  -> runtime uses frozen config unchanged
  -> INITIAL_PLANNING missing-master fallback creates one specialized task
  -> docs tell users to re-run liza init for new topology
```

## Cross-Cutting Concerns

| Concern | Approach |
|---------|----------|
| Error handling | Acceptance tests assert malformed topology and missing required refs fail through existing validation paths, while clean missing-master mappings use the documented one-specialized-task fallback. |
| Observability | Tests and docs cover `liza status`, task `role_pair`, status names, refs, `decomposition`, `transitions_executed`, and review quorum states as observable evidence. |
| Configuration | All behavior derives from embedded or frozen pipeline YAML. Docs emphasize frozen config immutability and avoid stack-specific project assumptions. |
| Testing | Combine focused package tests from parent scopes with cross-package integration scenarios for success criteria 1-8. Run `liza validate --json` plus targeted `go test` packages. |
| Documentation | Update user-facing and maintainer-facing docs in the same release as the behavior so entry-point routing, master responsibilities, schema, and non-migration boundaries are not tribal knowledge. |
| ADR | Add a new ADR and index entry for the cross-subpipeline master planning decision and its trade-offs. |
| Security and invariants | Keep all state mutations through existing commands/ops. Validation scenarios exercise no unreviewed fan-out, quorum gates, artifact-ref propagation, dependency direction, and absence of runtime migration. |

## Structural Decisions

### Decision 1: Put broad composition tests in one acceptance scope

The success criteria are system-level behaviors that span multiple packages. Parent scopes own focused unit and prompt tests; this scope owns the matrix proving the pieces compose. Keeping acceptance coverage together avoids four partial end-to-end tests that each miss the cross-domain failure modes.

### Decision 2: Keep documentation and ADR work separate from acceptance tests

Docs and ADRs touch durable human-facing artifacts and have a different review lens from executable validation. Splitting the scope keeps test implementation independent from prose updates while still letting both consume the same architecture artifact.

### Decision 3: Use existing integration patterns rather than a new harness

The repo already has tests for architecture-pair lifecycle, many-to-one fan-in, auto transitions, full sprint flows, and ref propagation. Extending those patterns reduces new infrastructure and keeps the acceptance layer close to existing behavior.

### Decision 4: Make non-migration an explicit tested and documented boundary

The goal spec says existing workspaces do not receive the new topology. The acceptance and docs scopes both treat that as a first-class boundary: no `MigrateOperations` path for master role-pairs, no implicit frozen-config rewrite, and clear re-initialization guidance.
