# Architecture Plan: Typed Decomposition Manifest and Artifact Propagation

Status: draft

## Goal

Define the implementation architecture for typed master `output[]` decomposition metadata, master-output validation, required master artifact refs, child task inheritance, and dependency propagation.

## Context

The master planning pattern requires decomposition-root tasks to emit a reviewed structural framework before specialized planning tasks fan out. The existing `output[]` channel already carries `desc`, `done_when`, `scope`, artifact refs, sibling `depends_on`, external `task_depends_on`, and `kind`. This plan extends that channel with typed decomposition metadata and tightens validation at the point where the full batch is available: `liza set-task-output`.

This plan covers the output-entry data contract and propagation layer only. Pipeline topology, decomposition-root resolver foundation, initial-planning routing, and master prompt sections are owned by sibling architecture tasks.

## Components

### Task Data Model (`internal/models/task.go`)

**Responsibility:** Own the persisted task and output-entry schema for decomposition metadata.

**Boundaries:**
- Exposes: `DecompositionManifest` type, `OutputEntry.Decomposition`, and task-level inherited decomposition metadata.
- Depends on: existing `OutputEntry` JSON/YAML decoding, kind validation, artifact refs, and dependency fields.

**Key decisions:**
- Add the goal-spec manifest as a concrete Go struct:
  - `OwnedFiles []string`
  - `OwnedModules []string`
  - `ReadOnlyDependsOn []int`
  - `ReadOnlyTaskDependsOn []string`
  - `InterfacesOwned []string`
  - `InterfacesConsumed []string`
  - `CoverageNotes string`
- Add `Decomposition *DecompositionManifest` to `OutputEntry`.
- Add `Decomposition *DecompositionManifest` to `Task` so child tasks inherit typed metadata as first-class state.
- Keep `ReadOnlyDependsOn` as `[]int` because it is a typed reference to sibling output indexes. Existing `OutputEntry.DependsOn` remains `[]string` for backward-compatible wire format.
- Do not add artifact-ref fields inside `DecompositionManifest`; refs stay in the existing `plan_ref`, `arch_ref`, and `epic_ref` fields protected by artifact-ref validators.

### Master Output Validator (`internal/ops/set_task_output.go`)

**Responsibility:** Validate an output batch before it is persisted onto the producing task.

**Boundaries:**
- Exposes: one validation path for ordinary output entries and stricter validation when the producer's role-pair is a decomposition root.
- Depends on: loaded pipeline resolver, task role-pair, `OutputConsumerRolePairs`, dependency-direction validation, artifact-ref scalar validation, and the decomposition-root metadata from `architecture-1`.

**Key decisions:**
- Keep existing universal validation for `desc`, `done_when`, `scope`, `kind`, artifact scalar shape, `depends_on`, `task_depends_on`, and dependency direction.
- Add a second pass after the task is read under the blackboard lock so validation can use the producer task's `RolePair` and the full output batch.
- For decomposition-root tasks, require every output entry to include `decomposition`.
- For non-root tasks, accept omitted `decomposition` and still validate shape when present.
- Required master artifact ref is determined from the producing role-pair:
  - `epic-planning-main-pair`: every entry must set `plan_ref`
  - `architecture-main-pair`: every entry must set `arch_ref`
  - `code-planning-main-pair`: every entry must set `plan_ref`
- The mapping should be implemented as a small role-pair-to-required-ref helper owned by the output validation layer, with tests proving unknown decomposition-root role-pairs fail closed.
- Validate `decomposition` batch-local invariants:
  - At least one ownership declaration across `owned_files`, `owned_modules`, or `interfaces_owned`.
  - No catch-all ownership values such as `everything else`, `all remaining`, or `*`.
  - No duplicate normalized `owned_files` across sibling entries.
  - No duplicate `interfaces_owned` across sibling entries.
  - `read_only_depends_on` entries are valid sibling indexes, are not self references, and are mirrored in `depends_on` for scheduling.
  - `read_only_task_depends_on` entries are valid existing task IDs and are mirrored in `task_depends_on`.
  - `depends_on` has no cycles across the output batch.
- Semantic questions remain reviewer-owned: meaningful domain boundaries, true interface ownership, and whole-goal coverage.

### Child Task Builder (`internal/ops/proceed.go`)

**Responsibility:** Convert a validated `OutputEntry` into a generated child task.

**Boundaries:**
- Exposes: child task state populated from output-entry fields.
- Depends on: upstream validation having already checked required refs, manifest shape, sibling indexes, and dependency direction.

**Key decisions:**
- Copy `entry.Decomposition` onto `Task.Decomposition` when building a child task.
- Preserve existing dependency merge behavior:
  - sibling `depends_on` indexes resolve to generated sibling task IDs;
  - `task_depends_on` concrete IDs are appended;
  - phase-gate inherited dependencies are appended;
  - duplicates are removed.
- Do not derive scheduler dependencies directly from `decomposition.read_only_depends_on`; `set-task-output` requires those metadata references to be mirrored in `depends_on`.
- Continue copying `entry.PlanRef` directly to `Task.PlanRef`.
- Continue copying `entry.ArchRef` and `entry.EpicRef` with existing parent fallback for compatibility.
- Do not add parent `plan_ref` fallback; master tasks must set the produced `plan_ref` on their output entries.

### Artifact Reference Validation (`internal/statevalidate`, existing)

**Responsibility:** Protect persisted refs against missing or unsafe artifact paths.

**Boundaries:**
- Exposes: scalar artifact-ref normalization and candidate-tree validation for task refs and output refs.
- Depends on: existing ref fields only.

**Key decisions:**
- Reuse current artifact-ref scalar checks in `set-task-output`.
- Reuse current candidate-tree artifact guards for `output[].plan_ref` and `output[].arch_ref`.
- Add tests for missing required master refs in `set-task-output`, not in generic state validation, because the requirement depends on the producer role-pair being a decomposition root.

### Inspection and Prompt Surfaces (`internal/commands`, optional prompt context)

**Responsibility:** Make inherited decomposition metadata visible wherever task state is rendered for agents or reviewers.

**Boundaries:**
- Exposes: typed decomposition fields in `liza get` / inspect JSON if those commands use explicit DTOs.
- Depends on: the task-level `Decomposition` field.

**Key decisions:**
- If existing command output already serializes full `models.Task`, no extra inspection work is required.
- If `inspect_tasks.go` uses explicit projection structs, add the task-level and output-level decomposition field to those projections with focused JSON tests.
- Do not edit master doer/reviewer prompt sections in this scope; those belong to `architecture-3`.

## Interfaces

### JSON/YAML Output Entry -> `models.OutputEntry`

**Contract:** `decomposition` is an optional nested object on all output entries and required when the producing task is a decomposition root.
**Direction:** CLI JSON decoding populates `models.OutputEntry` before `ops.SetTaskOutput` validation.
**Invariants:** Existing output entry fields keep their names and meanings. Unknown `kind` values are rejected. Artifact refs remain scalar repo-relative refs.

### Producing Task Role-Pair -> Master Validation Policy

**Contract:** `set-task-output` asks the resolver whether the producing role-pair is a decomposition root, then applies the required-ref and manifest rules for that root.
**Direction:** `ops.SetTaskOutput` loads the resolver and reads the current task under the blackboard lock.
**Invariants:** Non-root tasks retain backward compatibility. Root tasks fail closed if their required artifact ref cannot be determined.

### `OutputEntry` -> Child `Task`

**Contract:** A child task receives `Desc`, `DoneWhen`, `Scope`, `SpecRef`, artifact refs, `Kind`, scheduler dependencies, and `Decomposition` from the selected output entry.
**Direction:** `proceedInner` calls `buildChildTask` during `per-subtask` transition execution.
**Invariants:** `buildChildTask` does no semantic validation; malformed output must already be rejected by `set-task-output` or existing proceed validation.

## Data Flow

```
master doer writes artifact
  -> liza set-task-output receives output[] JSON
  -> SetTaskOutput validates ordinary fields
  -> SetTaskOutput detects decomposition-root producer
  -> master-only required refs and manifest invariants are checked
  -> output[] is persisted on the master task
  -> auto per-subtask transition runs after approval
  -> buildChildTask copies refs, deps, kind, and decomposition metadata
  -> specialized child task reads inherited plan_ref/arch_ref and decomposition state
```

Dependency flow:

```
output[i].depends_on          -> generated sibling task IDs
output[i].task_depends_on     -> existing concrete task IDs
phase-gate inherited deps     -> generated children of upstream dependencies
decomposition.read_only_*     -> validated metadata mirrored by the fields above
```

Artifact ref flow:

```
epic-planning-main output[].plan_ref       -> epic-planning-pair Task.PlanRef
architecture-main output[].arch_ref        -> architecture-pair Task.ArchRef
code-planning-main output[].plan_ref       -> code-planning-pair Task.PlanRef
specialized architecture output[].arch_ref -> code-planning-pair Task.ArchRef
specialized epic output[].epic_ref         -> us-writing-pair Task.EpicRef
```

## Cross-Cutting Concerns

| Concern | Approach |
|---------|----------|
| Error handling | Validation errors name task ID, output index, field, and conflicting sibling where applicable. Decomposition-root role-pairs with no known required ref fail closed. |
| Observability | Persisted task/output YAML and JSON include decomposition metadata; inspect DTOs are updated if they currently omit explicit fields. |
| Configuration | The only role-specific behavior is keyed by configured role-pair metadata and the goal-spec propagation table. No user-project stack assumptions are introduced. |
| Testing | Unit tests cover model serialization, root/non-root validation, duplicate/circular/catch-all rejection, required artifact refs, child task propagation, dependency merge preservation, and existing fallback behavior. |
| Backward compatibility | Existing non-root output entries remain valid without `decomposition`; existing `arch_ref` and `epic_ref` fallback behavior remains unchanged. |
| Security and invariants | Artifact refs continue through existing scalar and candidate-tree guards. Dependency direction validation remains the guard against downstream waits. |

## Structural Decisions

### Put Decomposition Validation in `SetTaskOutput`

`set-task-output` is the first point with the full output batch and the producing task role-pair. That makes it the correct owner for duplicate ownership, cycle detection, required master refs, and role-pair-sensitive requirements. `buildChildTask` stays a copier of already-validated state.

### Persist Manifest on Child Tasks

Output entries are historical producer state. Specialized tasks need their inherited ownership and interface metadata attached to their own task record so prompt construction, inspect commands, recovery, and reviewers can reason about the task without reverse-walking parent output arrays.

### Mirror Read-Only Manifest Dependencies into Scheduler Dependencies

`read_only_depends_on` and `read_only_task_depends_on` explain why the task consumes another entry or task. They do not create a second scheduler. Validation requires those references to be mirrored in `depends_on` and `task_depends_on`, preserving one scheduling source of truth.

### Required Refs Are Master-Output Rules, Not Generic State Rules

`plan_ref` and `arch_ref` are optional for ordinary outputs. They become required only for decomposition-root output entries because those entries create specialized planning tasks that inherit the master framework. Generic state validation stays shape-oriented; role-pair-specific requiredness belongs in `set-task-output`.

## Shared-File Audit

This plan has one output scope because the manifest schema, validation, and child propagation are one data-contract domain. Splitting model, validation, and propagation into separate output entries would create shared edits to `internal/models/task.go` and tightly coupled tests without creating independent user-visible domains.

The scope may consume contracts from the parent architecture replacement tasks:

- `architecture-1-code-planning-0-a`: `RolePairDef.DecompositionRoot` schema and validation.
- `architecture-1-code-planning-0-b`: resolver lookup or predicate for decomposition-root role-pairs.

This architecture output does not set `task_depends_on` on those current replacement tasks because they are `coding-pair` tasks and dependency-direction validation rejects downstream dependencies from an architecture-produced code-planning task. The code-planner should assign concrete coding-task dependencies when it decomposes this scope into coding tasks.
