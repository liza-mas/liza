# Architecture Plan: Master Decomposition Prompt Sections

Status: draft

## Goal

Define how decomposition-root planning tasks receive fixed master doer and reviewer prompt sections, how those sections render the Master Output Contract, and how focused prompt tests prove specialized tasks using the same roles do not inherit master-only instructions.

## Context

The goal spec adds master role-pairs that reuse existing doer and reviewer roles. That reuse creates a prompt-selection problem: `epic-planner`, `architect`, and `code-planner` must behave differently when the active task belongs to a `*-main-pair`, while ordinary specialized tasks with the same roles must keep their existing prompts.

`architecture-1` and its replacement implementation tasks provide the decomposition-root role-pair metadata, topology validation, resolver lookup, and embedded master pairs. `architecture-2-a` and `architecture-2-b` cover INITIAL_PLANNING routing and one-task wake prompt behavior. `architecture-4` covers typed decomposition manifest validation and child-task propagation. This plan covers only the master task prompt contract and prompt tests.

### Constraints

- Scope is planning only: no implementation, no pipeline YAML/schema/validation changes, no resolver implementation changes except consuming available metadata APIs, no `OutputEntry.DecompositionManifest` implementation, no `set-task-output` validation changes, no docs, and no ADR updates.

## Components

### Master Section Selector (`internal/agent/prompt.go`)

**Responsibility:** Decide whether task prompt construction should append a master-only prompt section after ordinary role context sections.

**Boundaries:**
- Exposes: doer/reviewer prompt section selection based on the active task's role-pair metadata.
- Depends on: `pipeline.Resolver.IsDecompositionRoot(rolePair)` and role type from the existing resolver.

**Key decisions:**
- Keep ordinary role `context-sections` in pipeline YAML unchanged.
- After resolving the role's normal context sections, ask the resolver whether `task.RolePair` is a decomposition root.
- If the task is a decomposition root and the current role is the pair's doer, append `master-decomposition-mandate`.
- If the task is a decomposition root and the current role is the pair's reviewer, append `master-decomposition-review`.
- If the task is not a decomposition root, append nothing.
- Resolver errors for the active task role-pair are prompt-build errors. A prompt that cannot determine whether it is rendering master obligations is unsafe to run.

### Master Prompt Data (`internal/prompts/role_context.go`)

**Responsibility:** Carry render-time data needed by both master prompt blocks without making the templates inspect topology.

**Boundaries:**
- Exposes: task role-pair and master artifact-ref field data to block templates.
- Depends on: prompt builder assigning fields after resolver checks.

**Key decisions:**
- Add prompt-safe fields equivalent to:
  - `IsDecompositionRootTask`
  - `MasterOutputRefField`
  - `MasterOutputRefPurpose`
- `MasterOutputRefField` resolves to `plan_ref` for `epic-planning-main-pair` and `code-planning-main-pair`, and `arch_ref` for `architecture-main-pair`.
- Unknown decomposition-root role-pairs fail closed during prompt construction rather than rendering incomplete output instructions.
- The template should render the field name, not duplicate the mapping in prose-only branches.

### Master Decomposition Mandate Block (`internal/prompts/templates/blocks/master_decomposition_mandate.tmpl`)

**Responsibility:** Instruct master doers to define the structural framework and emit typed `output[]` entries for specialized planning tasks.

**Boundaries:**
- Exposes: master-only doer instructions.
- Depends on: existing doer sections for task identity, tools, worktree rules, checkpoint/submission flow, and `set-task-output` mechanics.

**Key decisions:**
- State the doer responsibility boundary: define general approach, domain boundaries, interface contracts, shared-file ownership, dependency ordering, cross-cutting concerns, and coverage proof.
- State what master doers must not do: detailed implementation plans, specialized task content beyond boundaries/interfaces, pipeline schema changes, or validation behavior outside task scope.
- Render the Master Output Contract properties 1-6:
  1. non-overlapping scopes;
  2. interface ownership;
  3. shared-file ownership;
  4. dependency ordering;
  5. inherited constraints through the master artifact ref;
  6. completeness.
- Render the typed decomposition manifest field names from the goal spec as required output-entry metadata, while leaving validation to `architecture-4`.
- Render the required artifact-ref field as `{{.MasterOutputRefField}}` for every output entry.
- Require a `Systemic Decomposition Review` section in the master artifact containing either `No systemic issues identified.` or systemic-thinking findings in the skill's category format.
- Require the master doer to invoke `systemic-thinking` after drafting the decomposition and before `liza set-task-output` or submission, then revise the decomposition or surface unresolved structural findings.

### Master Decomposition Review Block (`internal/prompts/templates/blocks/master_decomposition_review.tmpl`)

**Responsibility:** Instruct master reviewers to evaluate decomposition quality, manifest obligations, artifact refs, and systemic coherence before verdict.

**Boundaries:**
- Exposes: master-only reviewer acceptance criteria.
- Depends on: existing reviewer sections for changed-file map, diff review, verdict submission, and review lifecycle.

**Key decisions:**
- Narrow master review to decomposition coherence: boundaries, ownership, dependencies, interface contracts, artifact refs, typed manifest presence, and spec coverage.
- Require rejection when any Master Output Contract property 1-6 is violated, even if individual entries look plausible in isolation.
- Require rejection when output entries omit the rendered master artifact-ref field or when the master artifact does not document the same decomposition.
- Require checking that the doer ran systemic-thinking by looking for the `Systemic Decomposition Review` artifact section.
- Require the reviewer to invoke `systemic-thinking` before verdict and use findings to reject unresolved structural tensions, assumptions, cascades, fragility, or stress points in the decomposition.
- Do not ask master reviewers to validate machine-enforced manifest invariants owned by `architecture-4` beyond prompt-level evidence and acceptance criteria.

### Prompt Tests (`internal/agent/prompt_test.go`, `internal/prompts/builder_test.go`)

**Responsibility:** Prove the rendered prompt contract across all master pairs and ordinary specialized pairs.

**Boundaries:**
- Exposes: regression tests for master-only section selection, artifact-ref field rendering, role-side separation, and old specialized prompt preservation.
- Depends on: embedded or fixture pipeline topology with `decomposition-root: true` role-pairs and resolver support from `architecture-1`.

**Key decisions:**
- Use task-level prompt construction tests for doer and reviewer prompts because the selector depends on `task.RolePair`, not only role name.
- Add focused block rendering tests only where they make acceptance text easier to assert than full prompt snapshots.
- Assert master doer prompts for `epic-planning-main-pair`, `architecture-main-pair`, and `code-planning-main-pair` contain `master-decomposition-mandate`, the Master Output Contract properties, systemic-thinking obligation, and the correct required output ref (`plan_ref`, `arch_ref`, `plan_ref`).
- Assert master reviewer prompts for the same pairs contain `master-decomposition-review`, rejection criteria for properties 1-6, systemic-thinking obligation, and the correct required output ref.
- Assert non-root `epic-planning-pair`, `architecture-pair`, and `code-planning-pair` prompts for the same roles contain no master block.
- Assert doer prompts do not contain the review block and reviewer prompts do not contain the mandate block.

## Interfaces

### Pipeline Resolver -> Prompt Builder

**Contract:** Given the active task role-pair, the resolver reports whether it is explicitly marked as a decomposition root. Prompt builder treats a true result as the only trigger for master sections.
**Direction:** `buildPromptWithContext` calls resolver metadata APIs while constructing section names and master prompt data.
**Invariants:** No prompt behavior is inferred from outgoing `per-subtask` transitions. Specialized planning pairs that also fan out never receive master sections unless their own role-pair is explicitly marked `decomposition-root: true`.

### Prompt Builder -> Role Context Renderer

**Contract:** `BuildRoleContext` receives the ordinary role context sections plus any computed master section name, and `RoleContextData` includes the resolved artifact-ref field.
**Direction:** Agent prompt construction prepares section names and data; `internal/prompts` renders blocks in order.
**Invariants:** The renderer stays a generic block concatenator. It does not know pipeline topology or decide whether a task is a master task.

### Master Doer Prompt -> `liza set-task-output`

**Contract:** A master doer writes a master artifact, then emits one `output[]` entry per specialized scope with the required artifact ref and typed decomposition metadata.
**Direction:** The prompt guides the doer; `architecture-4` owns validation of the resulting output structure.
**Invariants:** Prompt text must not instruct parent task artifact-ref mutation. The artifact ref is carried on each output entry.

### Master Reviewer Prompt -> Verdict

**Contract:** A master reviewer approves only if the artifact plus `output[]` satisfy the Master Output Contract, artifact-ref requirements, systemic-thinking obligations, and reviewer acceptance criteria.
**Direction:** Reviewer reads the diff, artifact, and `liza get <task-id> --json`, then submits a verdict.
**Invariants:** Quorum reviewers independently apply the same acceptance criteria. A decomposition that is locally plausible but globally incoherent is rejected.

## Data Flow

Master doer prompt flow:

```text
task.RolePair
  -> resolver.IsDecompositionRoot
  -> role type is doer
  -> append master-decomposition-mandate
  -> render required output ref field
  -> doer writes master artifact and output[]
```

Master reviewer prompt flow:

```text
task.RolePair
  -> resolver.IsDecompositionRoot
  -> role type is reviewer
  -> append master-decomposition-review
  -> render acceptance criteria and required output ref field
  -> reviewer runs systemic-thinking and submits verdict
```

Specialized task flow:

```text
task.RolePair is not a decomposition root
  -> ordinary role context sections only
  -> specialized doer/reviewer responsibilities remain unchanged
```

Artifact-ref rendering flow:

```text
epic-planning-main-pair output[]       -> plan_ref points to master plan artifact
architecture-main-pair output[]        -> arch_ref points to master architecture artifact
code-planning-main-pair output[]       -> plan_ref points to master code-planning artifact
```

## Cross-Cutting Concerns

| Concern | Approach |
|---------|----------|
| Error handling | Prompt construction fails when a decomposition-root role-pair has no known output artifact-ref field or when resolver metadata cannot be read. Rendering an incomplete master prompt is treated as unsafe. |
| Observability | Master prompt obligations are visible in saved agent prompts and reviewer verdict criteria. The master artifact records systemic-thinking results in a dedicated section. |
| Configuration | Ordinary context sections remain role-level YAML. Master additions are fixed sections selected by `decomposition-root: true`; no arbitrary role-pair context override is introduced. |
| Testing | Tests cover all three master pairs, all three specialized pairs, both role sides, artifact-ref rendering, systemic-thinking obligations, and absence of master sections on non-root tasks. |
| Backward compatibility | Existing frozen/custom pipelines without decomposition-root role-pairs render unchanged prompts. Optional resolver absence for old role-pairs produces no master sections when the active role-pair is known and unmarked. |
| Security and invariants | No new state mutation path is introduced. The prompt reinforces CLI-only `set-task-output` usage and reviewer rejection of unreviewed fan-out or missing constraints. |

## Structural Decisions

### Decision 1: Select master sections in agent prompt construction

The decision needs both active task role-pair and current role side. `BuildRoleContext` only receives section names and should remain a generic renderer. The selector therefore belongs in `internal/agent/prompt.go`, which already has the task, role type, resolver, and prompt data.

### Decision 2: Keep master sections fixed

The goal spec explicitly rejects `RolePairDef.context-sections`. Fixed sections avoid creating a second prompt configuration system and keep review criteria uniform across epic, architecture, and code-planning masters.

### Decision 3: Render artifact-ref field from prompt data

The same mandate/review blocks apply to all master pairs, but the required output ref differs by planning step. Supplying one resolved field name lets the templates stay shared while tests prove the three concrete mappings.

### Decision 4: Require recorded systemic-thinking output

The prompt cannot prove a skill was invoked unless the artifact carries evidence. A dedicated `Systemic Decomposition Review` section gives reviewers a concrete check and gives specialized downstream planners durable context for structural tensions.

### Decision 5: Preserve ordinary specialized prompts

Role reuse is the point of the design. Specialized tasks using `epic-planner`, `architect`, and `code-planner` must not see master decomposition obligations, because those obligations would incorrectly invite them to redefine boundaries already inherited from a master artifact.

## Shared-File Audit

This plan emits one code-planning scope because section selection, prompt data, block templates, and prompt tests form one prompt-contract domain. Splitting them would create shared edits to `internal/agent/prompt.go`, `internal/prompts/role_context.go`, and prompt tests without producing independent implementation value.

Potential sibling and upstream overlaps:

- `architecture-2-a-code-planning-0` and `architecture-2-b-code-planning-0` may also touch `internal/prompts` tests and wake templates, but they own INITIAL_PLANNING routing. This scope must avoid `wake_initial_planning.tmpl` and confine prompt tests to master doer/reviewer role prompts.
- `architecture-4` owns `internal/models/task.go`, `internal/ops/set_task_output.go`, and `internal/ops/proceed.go` for manifest validation and propagation. This scope may mention typed metadata in templates but must not implement schema or validation.
- `architecture-1-code-planning-0-b` and `architecture-1-code-planning-0-c` provide resolver and topology contracts. This scope consumes their APIs and topology. This architecture task cannot declare them in `task_depends_on` because its output creates a `code-planning-pair` child and dependency-direction validation rejects downstream coding-pair dependencies; downstream code-planning output entries must carry any still-needed concrete coding dependencies.
