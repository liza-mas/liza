# Architecture Plan: Pipeline Topology and Master Role-Pair States

Status: draft

## Goal

Define the pipeline topology foundation for the master planning task pattern: master role-pairs, quorum states, decomposition-root metadata validity, intra-subpipeline auto-decompose transitions, and cross-subpipeline routing for Case A and Case B.

## Context

The goal spec introduces a master-task pattern for every planning fan-out. This plan covers the structural pipeline layer only. It does not plan prompt text, output-entry manifest validation, initial-planning prompt behavior, or documentation; those are owned by downstream architecture tasks that depend on this task.

The existing system already has declarative role-pairs, role-pair states, sub-pipelines, `per-subtask` and `many-to-one` transitions, quorum states, and transition target helpers. The change should extend those existing mechanisms instead of adding a new pipeline primitive.

## Components

### Embedded Pipeline Topology (`internal/embedded/pipeline.yaml`)

**Responsibility:** Own the default role-pair, sub-pipeline, transition, and entry-point topology frozen into new workspaces.

**Boundaries:**
- Exposes: declarative role-pairs, states, sub-pipeline steps, intra-subpipeline transitions, pipeline transitions, and entry-points.
- Depends on: `internal/pipeline/config.go` schema and validation accepting the declared fields.

**Key decisions:**
- Add three master role-pairs:
  - `epic-planning-main-pair`
  - `architecture-main-pair`
  - `code-planning-main-pair`
- Reuse existing doer/reviewer roles for each master pair.
- Set `decomposition-root: true` and `review-policy: { quorum: 2, provider-diversity: preferred }` on each master pair.
- Declare the quorum states on each master pair because base quorum is 2.
- Insert master steps before specialized steps inside the relevant sub-pipelines.
- Add one auto `per-subtask` decomposition transition from each master pair to its specialized pair.
- Leave entry-points targeting specialized pairs. Initial planning will choose the master pair only when fan-out is needed; `architecture-2` owns that prompt/template behavior.
- Retarget `us-to-coding` to `architecture-subpipeline.architecture-main-pair.initial`.
- Leave `architecture-to-code-plan` source as `architecture-subpipeline.architecture-pair.approved` and target as `coding-subpipeline.code-planning-pair.initial`, preserving Case A bypass.

### Pipeline Schema and Validation (`internal/pipeline/config.go`)

**Responsibility:** Parse and reject invalid declarative pipeline configurations before runtime components consume them.

**Boundaries:**
- Exposes: `RolePairDef.DecompositionRoot bool` parsed from `decomposition-root`.
- Depends on: role-pair maps and sub-pipeline transition definitions already parsed by `PipelineConfig`.

**Key decisions:**
- Add a boolean `decomposition-root` field to `RolePairDef`; do not introduce generic role-pair context sections.
- Validation should require a decomposition-root role-pair to have exactly one outgoing intra-subpipeline transition with:
  - `from: <root-pair>.approved`
  - `trigger: auto`
  - `cardinality: per-subtask`
  - a target role-pair in the same sub-pipeline
- Validation should reject decomposition-root markers on terminal role-pairs, markers with zero outgoing decomposition transitions, markers with more than one outgoing decomposition transition, non-auto transitions, non-`per-subtask` transitions, or transitions whose target is outside the same sub-pipeline.
- Existing `validateQuorumStates` remains the enforcement point for required quorum states. The master pairs use base quorum 2, so missing `partially-approved` or `reviewing-2` should fail through that existing validator.

### Resolver Topology API (`internal/pipeline/resolver.go`)

**Responsibility:** Provide topology queries for consumers without duplicating YAML traversal logic.

**Boundaries:**
- Exposes: a specialized-to-master lookup for entry-point routing and prompt data, plus a role-pair predicate for decomposition roots.
- Depends on: validated `RolePairDef.DecompositionRoot` and validated auto `per-subtask` transitions.

**Key decisions:**
- Add resolver methods at topology altitude, not prompt altitude:
  - `IsDecompositionRoot(rolePair string) (bool, error)`
  - `DecompositionRootForTarget(targetRolePair string) (string, bool, error)` or equivalent naming consistent with existing resolver methods
- The lookup must use the explicit `decomposition-root` marker and the validated auto transition target. It must not infer master behavior from any outgoing `per-subtask` transition because specialized planning pairs also fan out.
- Return `(root, true, nil)` when exactly one validated root targets the specialized pair and `("", false, nil)` when no root exists. Multiple roots should be impossible after config validation; if observed, return an error.

### Transition Consumers (`internal/ops`, `internal/agent`, `internal/prompts`)

**Responsibility:** Consume the existing transition graph for runtime work detection, manual transition execution, auto transition execution, and prompt data.

**Boundaries:**
- Exposes: no new transition primitive.
- Depends on: the topology and resolver methods above.

**Key decisions:**
- Intra-subpipeline decomposition uses existing `auto` plus `per-subtask` semantics. The code-planning task should verify existing auto-transition execution covers the new transitions; if a missing runtime path is found, wire it generically for all auto transitions rather than adding master-task special cases.
- `liza proceed` remains manual-only. Auto decompose transitions are supervisor/runtime driven, matching existing `integration-to-fix` semantics.
- `architecture-2` may consume the resolver specialized-to-master lookup in `buildWakeTemplateData`; this plan owns the resolver contract but not the wake template behavior.

## Interfaces

### Embedded Pipeline YAML -> Pipeline Config

**Contract:** YAML role-pairs may include `decomposition-root: true`. The field is optional and defaults to false.
**Direction:** `pipeline.Load` and `pipeline.LoadFrozen` parse YAML into `PipelineConfig`.
**Invariants:** Unknown YAML fields still fail due to `KnownFields(true)`. Invalid decomposition-root topology fails during config validation before a resolver is constructed.

### Pipeline Config -> Resolver Topology Queries

**Contract:** Consumers ask the resolver whether a role-pair is a decomposition root or which root targets a specialized role-pair.
**Direction:** Prompt and orchestration code call resolver methods; they do not traverse `PipelineConfig` directly.
**Invariants:** Resolver mapping is based on explicit `decomposition-root: true` and validated auto `per-subtask` transition targets only.

### Approved Master Task -> Auto Decompose Transition

**Contract:** Once a master task reaches its approved state and is merged, the auto transition creates one specialized child per `output[]` entry.
**Direction:** Runtime transition detection sees the approved state and uses the configured auto transition to create children.
**Invariants:** The child target is the specialized role-pair initial state. Output-entry dependencies and artifact refs are copied by existing child creation paths and are further planned by `architecture-4`.

### Cross-Subpipeline Routing

**Contract:** `us-to-coding` creates an `architecture-main-pair` task from a many-to-one story cohort. `architecture-to-code-plan` creates `code-planning-pair` tasks from specialized architecture output.
**Direction:** Manual pipeline transitions call the existing transition machinery with retargeted YAML.
**Invariants:** `architecture-to-code-plan` never targets `code-planning-main-pair`; architecture already provides consolidation for Case A.

## Data Flow

```
embedded pipeline.yaml
  -> pipeline.LoadFrozen / validate
  -> pipeline.NewResolver
  -> runtime consumers
       - initial planning prompt data uses specialized-to-master lookup
       - auto transition detection sees approved master states
       - manual transitions use retargeted top-level pipeline transitions
```

Case B entry-point fan-out flow:

```
INITIAL_PLANNING classifies complex entry work
  -> resolver maps specialized target to decomposition-root role-pair
  -> one master task is created
  -> quorum 2 approval reaches <MASTER>_APPROVED
  -> auto per-subtask decompose transition creates specialized children
```

Case A architecture-to-code-plan flow:

```
architecture-pair approved specialized architecture task
  -> manual architecture-to-code-plan transition
  -> one code-planning-pair child per output[] entry
  -> code-planning-main-pair is bypassed
```

US-to-coding many-to-one flow:

```
approved us-writing-pair cohort
  -> manual us-to-coding transition
  -> one architecture-main-pair task
  -> master architecture task decomposes into specialized architecture tasks after quorum approval
```

## Cross-Cutting Concerns

| Concern | Approach |
|---------|----------|
| Error handling | Invalid topology is rejected at pipeline load with role-pair and transition names in the error. Runtime consumers should not need to recover from malformed decomposition-root mappings. |
| Observability | Existing transition history remains authoritative. Auto decompose transitions should record the normal transition-executed history used by other auto transitions. |
| Configuration | All topology is declarative in `pipeline.yaml`; no stack-specific project command, path, or build-system assumption is introduced. |
| Testing | Unit-test schema parsing, validation failures, resolver mapping, fixture/embedded topology, and transition target resolution. End-to-end verification is owned by `architecture-5`. |
| Backward compatibility | Existing frozen workspaces are unchanged. The new `decomposition-root` field is optional, so existing pipeline YAML remains valid. |
| Security and invariants | The design preserves state mutation through existing ops and blackboard locking. It adds validation before runtime state creation to protect out-of-order progression and unreviewed fan-out. |

## Decomposition

Each scope becomes a code-planning child task.

### Scope 1: Pipeline topology and decomposition-root resolver foundation

**Component(s):** Embedded pipeline topology, pipeline schema/validation, resolver topology API, and transition-target fixtures.

**Boundary:** In scope: `internal/embedded/pipeline.yaml`, `internal/pipeline/config.go`, `internal/pipeline/resolver.go`, `internal/pipeline/config_test.go`, `internal/pipeline/resolver_test.go`, `internal/pipeline/testdata/valid-phase2-full.yaml`, and focused command/JSON wiring tests only if they assert embedded pipeline validity. Out of scope: initial-planning prompt wording and task creation behavior, master prompt sections, typed decomposition manifest schema/validation, artifact-ref propagation, documentation updates, ADR authoring, and broad end-to-end scenario tests owned by downstream architecture tasks.

**Done when:** `RolePairDef` parses optional `decomposition-root`; the embedded default pipeline and phase2 fixture declare `epic-planning-main-pair`, `architecture-main-pair`, and `code-planning-main-pair` with quorum 2, provider-diversity preferred, required quorum states, auto `per-subtask` decompose transitions, retargeted `us-to-coding`, and Case A `architecture-to-code-plan` bypass; pipeline validation rejects invalid decomposition-root configurations for zero, multiple, non-auto, non-`per-subtask`, cross-subpipeline, or non-approved-source decomposition transitions; resolver tests prove specialized role-pairs map to their root role-pairs only through explicit decomposition-root metadata; `liza validate --json` and `go test ./internal/pipeline/...` exit 0.

**Depends on:** none.

**Output desc:** Add the pipeline topology and resolver foundation for master planning tasks: optional `RolePairDef.DecompositionRoot` parsed from `decomposition-root`, validation that a decomposition-root role-pair has exactly one outgoing same-subpipeline auto `per-subtask` transition from its approved phase to a specialized role-pair, resolver lookup from specialized role-pair to its decomposition-root role-pair, embedded pipeline updates for the three master role-pairs with quorum 2 states, intra-subpipeline auto-decompose transitions, `us-to-coding` retargeting to `architecture-main-pair`, and Case A `architecture-to-code-plan` bypass to `code-planning-pair`.

**Output scope:** `internal/pipeline/config.go` and tests for `decomposition-root` schema/validation; `internal/pipeline/resolver.go` and tests for decomposition-root lookup; `internal/embedded/pipeline.yaml` and `internal/pipeline/testdata/valid-phase2-full.yaml` for topology changes; focused pipeline fixture or JSON wiring tests only when needed to prove the embedded pipeline loads. Do not modify initial planning wake templates, master prompt sections, output-entry `DecompositionManifest`, `set-task-output` validation, artifact propagation, docs, or ADR files in this scope.

**Output done_when:** `RolePairDef` has an optional `DecompositionRoot bool` field with YAML tag `decomposition-root,omitempty`; the embedded pipeline and `valid-phase2-full.yaml` contain `epic-planning-main-pair`, `architecture-main-pair`, and `code-planning-main-pair` with `review-policy.quorum: 2`, `provider-diversity: preferred`, `partially-approved` and `reviewing-2` states, and one auto `per-subtask` decompose transition from each main pair approved phase to its specialized pair initial phase; `us-to-coding` targets `architecture-subpipeline.architecture-main-pair.initial`; `architecture-to-code-plan` targets `coding-subpipeline.code-planning-pair.initial` and does not reference `code-planning-main-pair`; validation tests reject decomposition-root configs with zero outgoing decomposition transition, multiple outgoing decomposition transitions, non-auto trigger, non-`per-subtask` cardinality, cross-subpipeline target, or non-approved source phase; resolver tests show `epic-planning-pair`, `architecture-pair`, and `code-planning-pair` map to their respective main pairs while non-specialized pairs return no root; `go test ./internal/pipeline/...` and `liza validate --json` both exit 0.
