# Architecture Plan: INITIAL_PLANNING One-Task Prompt Contract

Status: draft

## Goal

Define the prompt-level contract for `wake_initial_planning.tmpl` so initial planning creates exactly one specialized planning task for simple goals, or exactly one mapped master planning task for fan-out or uncertain goals.

## Context

The goal spec removes INITIAL_PLANNING's direct multi-task fan-out responsibility. The orchestrator still classifies entry-point work and judges whether the goal is simple or needs decomposition, but it no longer decomposes directly into several parallel planning tasks. For simple goals it creates one specialized planning task. For fan-out or uncertain goals it creates one master task in the decomposition-root role-pair mapped from the specialized entry-point target.

`architecture-2-a` defines the wake data contract that exposes both routing choices to the template: a specialized simple target for every entry-point and an optional resolver-mapped fan-out master target. This plan consumes that data contract and scopes the downstream work to template wording, task JSON examples, heuristic rendering, and prompt rendering tests.

## Components

### INITIAL_PLANNING Wake Template (`internal/prompts/templates/wake_initial_planning.tmpl`)

**Responsibility:** Render the orchestrator's one-task routing instructions and task JSON examples from already-resolved entry-point routing data.

**Boundaries:**
- Exposes: prompt text that tells the orchestrator how to choose one route and create one task with `liza add-tasks`.
- Depends on: `wakeTemplateData` and `wakeEntryPointData` fields supplied by `architecture-2-a`.

**Key decisions:**
- Replace the current "single or multiple tasks" and "MULTI-TASK PLANNING" language with a simple-vs-fan-out routing rule.
- Render simple goals as exactly one specialized planning task using the simple target role-pair, type, display name, and ID prefix.
- Render fan-out and uncertain goals as exactly one mapped master planning task when a fan-out target exists.
- Render no two-object task array examples for INITIAL_PLANNING. Examples must show one JSON object in the bare JSON array.
- Keep `liza add-tasks` as the only state mutation path.

### Simple-vs-Fan-Out Heuristic Text (`internal/prompts/templates/wake_initial_planning.tmpl`)

**Responsibility:** Give the orchestrator a concrete decision rule without returning decomposition responsibility to the orchestrator.

**Boundaries:**
- Exposes: criteria for simple, fan-out, and uncertain goals.
- Depends on: goal spec content and entry-point classification.

**Key decisions:**
- Simple means one coherent planning scope: one functional area, no shared file/schema/interface ownership question, no migration or cross-cutting contract needing explicit ownership, and no expected downstream split into independent specialized scopes.
- Fan-out means multiple functional areas, shared ownership boundaries, independent downstream workstreams, likely more than 8 downstream `output[]` entries, or uncertainty about boundary placement.
- Uncertainty routes to the master task, not to multiple specialized tasks.

### Task JSON Example Contract (`internal/prompts/templates/wake_initial_planning.tmpl`)

**Responsibility:** Show valid `liza add-tasks` JSON for exactly one created task.

**Boundaries:**
- Exposes: bare JSON array examples with one object.
- Depends on: resolved simple target fields and resolved fan-out target fields.

**Key decisions:**
- Simple example uses the specialized role-pair and task type.
- Fan-out example uses the mapped master role-pair and task type.
- Examples use one task ID with the route-specific prefix and no second suffix entry.
- `depends` remains empty because there is only one task at INITIAL_PLANNING.

### Prompt Rendering Tests (`internal/prompts/builder_test.go` and focused prompt helpers)

**Responsibility:** Prove INITIAL_PLANNING renders the one-task contract and the correct specialized/master role-pair targets.

**Boundaries:**
- Exposes: regression tests for explicit entry-points, classification rendering, old multi-task guidance removal, fan-out defaulting on uncertainty, and missing-master fallback if the data contract has no fan-out target.
- Depends on: production embedded pipeline where possible, and focused pipeline fixtures when the embedded topology is not yet carrying master role-pairs.

**Key decisions:**
- Assert each explicit entry-point renders the specialized simple route and the mapped master fan-out route:
  - `general-objective`: `epic-planning-pair` and `epic-planning-main-pair`
  - `functional-spec`: `architecture-pair` and `architecture-main-pair`
  - `detailed-spec`: `architecture-pair` and `architecture-main-pair`
  - `technical-spec`: `code-planning-pair` and `code-planning-main-pair`
- Assert the no-entry-point classification view presents both simple and fan-out target choices for each entry-point when mappings exist.
- Assert the rendered prompt does not contain the old multi-task fan-out instructions such as "MULTI-TASK PLANNING", "Create up to", same role-pair for all tasks, or domain A/domain B two-task arrays.
- Assert prompt output requires exactly one task for simple, fan-out, and uncertain cases.

## Interfaces

### `architecture-2-a` Wake Data Contract -> Wake Template

**Contract:** The template receives route data that separates specialized simple targets from optional mapped fan-out master targets. Route data includes role-pair, task type, display name, and task ID prefix for each target, plus a boolean indicating whether a fan-out target exists.
**Direction:** `buildWakeTemplateData` constructs the data; `wake_initial_planning.tmpl` consumes it.
**Invariants:** The template must not derive master role-pair names by string manipulation and must not inspect pipeline topology.

### Wake Template -> Orchestrator Task Creation

**Contract:** The rendered prompt instructs the orchestrator to write a bare JSON array accepted by `liza add-tasks`, containing exactly one object for the selected route.
**Direction:** The orchestrator follows the prompt and runs `liza add-tasks --tasks-file <path.json> --agent-id <id> --json`.
**Invariants:** INITIAL_PLANNING creates one task only. Complex or uncertain goals create one master task when a fan-out target exists; they do not create N specialized tasks.

### Prompt Tests -> Rendered Prompt

**Contract:** Tests evaluate rendered wake instructions as the observable behavior, using stable strings tied to routing guarantees rather than incidental prose.
**Direction:** `RenderOrchestratorDashboard` or focused template helpers render INITIAL_PLANNING instructions; tests assert target role-pairs, task types, and absence of old fan-out guidance.
**Invariants:** Tests must reject prompts that allow multiple INITIAL_PLANNING tasks or route fan-out to specialized role-pairs when a master mapping exists.

## Data Flow

```text
Goal spec + optional entry-point
  -> wake route data from architecture-2-a
  -> INITIAL_PLANNING prompt renders simple and fan-out route choices
  -> orchestrator selects exactly one route
  -> one-object bare JSON array
  -> liza add-tasks creates exactly one planning task
```

Explicit entry-point flow:

```text
Goal.EntryPoint
  -> selected entry-point route data
  -> simple case: specialized target example
  -> fan-out/uncertain case: mapped master target example
  -> one task created
```

Classification flow:

```text
No Goal.EntryPoint
  -> classify as general-objective, functional-spec, detailed-spec, or technical-spec
  -> apply same simple-vs-fan-out heuristic
  -> choose either the entry-point simple target or mapped master target
  -> one task created
```

Missing-master fallback flow:

```text
Entry-point has no fan-out target
  -> template cannot render an invented master route
  -> prompt falls back to one specialized planning task for the whole planning scope
  -> one task created
```

## Cross-Cutting Concerns

| Concern | Approach |
|---------|----------|
| Error handling | Resolver and data-construction errors remain owned by `architecture-2-a`; the template renders only provided route data. Missing fan-out target is handled explicitly as one-task specialized fallback. |
| Observability | The created task's `role_pair`, `type`, and ID prefix reveal whether the simple or master route was chosen. |
| Configuration | Role-pair names come from pipeline-derived data, not hardcoded template derivation. Test fixtures may name canonical master pairs to assert the contract. |
| Testing | Prompt tests assert observable rendered instructions, exact one-task examples, specialized/master targets, and absence of old multi-task guidance. |
| Backward compatibility | Custom or frozen configs with no master mapping render one specialized task instead of reintroducing parallel fan-out. |
| Security | The prompt continues to use `liza add-tasks`; no direct blackboard edits or new state mutation path are introduced. |
| Stack agnosticism | Prompt wording avoids project build commands, language assumptions, or Liza-internal project paths outside the Liza CLI task-creation command. |

## Structural Decisions

### Decision 1: Make one-task routing the first-class prompt contract

The existing template frames INITIAL_PLANNING as "single task or multiple tasks". That is the behavior being removed. The new prompt should state that both branches create exactly one task, and that the distinction is the target role-pair: specialized for simple, master for fan-out or uncertainty.

### Decision 2: Keep decomposition criteria but move decomposition work to master tasks

The orchestrator still needs enough heuristic guidance to decide whether a master task is needed. It must not receive instructions to partition domains itself. The prompt should ask it to assess whether partitioning would be needed, then create one master task when the answer is yes or uncertain.

### Decision 3: Test for absence of the old contract

Positive assertions on the new role-pairs are not enough. A prompt containing both new master guidance and old "create up to 5 tasks" guidance would still be unsafe. Prompt tests should assert removal of the old multi-task strings and two-task examples.

### Decision 4: Use focused fixtures for master mappings when embedded YAML lags topology work

The current worktree already contains resolver support and resolver tests for decomposition-root mappings, while embedded pipeline topology is owned by other tasks. Prompt tests should use production embedded data when it can express the route, and focused fixtures when the production config cannot yet expose all master mappings. This keeps this scope unblocked without taking ownership of topology changes.
