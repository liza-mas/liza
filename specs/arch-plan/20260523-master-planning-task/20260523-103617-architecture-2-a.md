# Architecture Plan: INITIAL_PLANNING Master Routing Wake Data

Status: draft

## Goal

Define the INITIAL_PLANNING wake data contract that lets the orchestrator create exactly one specialized planning task for simple entry-point work, or exactly one mapped master planning task when the same entry-point would otherwise fan out.

## Context

The goal spec changes initial planning from direct fan-out into multiple specialized planning tasks to a simple-vs-fan-out routing decision. Entry-points still name specialized role-pairs, but fan-out work must route to the decomposition-root role-pair mapped to that specialized pair by the pipeline resolver.

This plan covers the prompt data and rendering contract only. The pipeline topology and resolver foundation are planned by `architecture-1`; master prompt sections, output-entry decomposition validation, artifact propagation, broad end-to-end validation, docs, and ADR work are out of scope for this task.

### Constraints

- Scope is planning only: no implementation, no wake template prose, no prompt block templates, no pipeline YAML/schema/validation, no output-entry manifest validation, no artifact propagation, no docs, and no ADR updates.

- Master routing must not infer behavior from generic `per-subtask` fan-out. The resolver contract from `architecture-1` is the only source of master mapping.
- `liza add-tasks` already validates `role_pair`, derives task type when omitted, and assigns the role-pair initial status. This plan keeps task creation through that existing operation.

## Components

### Wake Data Builder (`internal/prompts/wake.go`)

**Responsibility:** Resolve entry-point routing data from the frozen pipeline config into template-ready simple-target and fan-out-target fields.

**Boundaries:**
- Exposes: `wakeTemplateData` and `wakeEntryPointData` containing explicit routing targets for INITIAL_PLANNING.
- Depends on: `pipeline.LoadFrozen`, `pipeline.NewResolver`, role-pair display/type helpers, and the decomposition-root resolver lookup from `architecture-1`.

**Key decisions:**
- Keep entry-point YAML values as specialized simple targets.
- For each specialized target, ask the resolver for the mapped decomposition-root role-pair.
- Populate a simple target for every entry-point.
- Populate a fan-out target only when the resolver finds a decomposition-root mapping.
- Derive display name, task ID prefix, and task type for both targets through existing resolver/model helpers rather than hardcoded role-pair names.
- Keep explicit-entry-point data and classification-entry data structurally aligned so the template does not need a separate hardcoded path.

### Wake Route Data Contract (`internal/prompts/wake.go`)

**Responsibility:** Make the routing choice explicit in data instead of burying it in template conditionals or prose.

**Boundaries:**
- Exposes per entry-point:
  - entry-point name
  - simple target role-pair
  - simple target task type
  - simple target doer display name
  - simple target task ID prefix
  - optional fan-out target role-pair
  - optional fan-out target task type
  - optional fan-out target doer display name
  - optional fan-out target task ID prefix
  - boolean indicating whether a fan-out target exists
- Depends on: resolver role-pair lookups and task-type derivation from the target role-pair's doer role.

**Key decisions:**
- Use a boolean such as `HasFanOutTarget` rather than interpreting an empty string in the template.
- Keep simple and fan-out target fields separate. This prevents complex-case task JSON from accidentally reusing the specialized role-pair.
- For explicit `--entry-point`, copy the selected entry-point's simple and fan-out fields into resolved fields on `wakeTemplateData`; do not recompute them through a divergent path.

### INITIAL_PLANNING Template Consumer (`internal/prompts/templates/wake_initial_planning.tmpl`)

**Responsibility:** Render task-creation instructions from the data contract.

**Boundaries:**
- Exposes: no new state mutation path; still instructs the orchestrator to write a JSON array and call `liza add-tasks`.
- Depends on: `wakeTemplateData` fields for simple and fan-out targets.

**Key decisions:**
- Simple case renders a single task using the specialized simple target.
- Fan-out case renders a single task using the mapped master target when `HasFanOutTarget` is true.
- Missing-master fallback renders no master target and therefore cannot instruct a master task. The fallback is one specialized planning task for the whole entry-point scope, preserving the "exactly one task" invariant and avoiding the old parallel fan-out behavior.
- Do not introduce exact wake prose in this plan. The code-planning task owns wording while preserving these data semantics.

### Resolver Topology API (`internal/pipeline/resolver.go`)

**Responsibility:** Provide the specialized-to-master mapping consumed by wake data construction.

**Boundaries:**
- Exposes: the decomposition-root lookup planned by `architecture-1`.
- Depends on: validated `decomposition-root: true` metadata and the auto `per-subtask` transition from a root role-pair to its specialized role-pair.

**Key decisions:**
- Wake data construction consumes the resolver API. It must not scan sub-pipelines or inspect transitions directly.
- Resolver lookup errors are hard failures because they indicate malformed topology or resolver inconsistency.
- A clean "not found" result is not an error; it drives the missing-master fallback for legacy/custom configs.

### Prompt Tests (`internal/prompts/builder_test.go` and focused helpers)

**Responsibility:** Prove rendered INITIAL_PLANNING instructions use the correct role-pair/type data for simple and fan-out routes.

**Boundaries:**
- Exposes: regression coverage for explicit entry-points, classification listing, missing-master fallback, and resolver errors.
- Depends on: embedded/frozen pipeline test setup and any focused helper tests for route-data construction.

**Key decisions:**
- Update explicit entry-point tests to assert both specialized simple targets and mapped master fan-out targets where the pipeline has a decomposition-root mapping.
- Add a missing-master fallback fixture where an entry-point has no mapped master; assert the rendered output does not contain an invented master role-pair and still contains one specialized target.
- Add route-data tests around the wake data builder if template assertions alone would make failures hard to diagnose.

## Interfaces

### Pipeline Resolver -> Wake Data Builder

**Contract:** Given a specialized entry-point role-pair, the resolver returns `(masterRolePair, true, nil)` when a validated decomposition-root role-pair targets it, `("", false, nil)` when no mapping exists, or an error for inconsistent topology.
**Direction:** `buildWakeTemplateData` calls the resolver while constructing `wakeEntryPointData`.
**Invariants:** The wake package never infers master status from outgoing transitions. Only explicit resolver metadata can produce a fan-out target.

### Wake Data Builder -> INITIAL_PLANNING Template

**Contract:** The template receives simple target fields for every entry-point and fan-out target fields only when a master mapping exists.
**Direction:** `buildInstructionsForWakeTrigger("INITIAL_PLANNING", ...)` passes `wakeTemplateData` into `wake_initial_planning`.
**Invariants:** Simple and fan-out role-pair/type/prefix/display fields are already resolved before template execution. The template chooses between provided targets; it does not resolve pipeline topology.

### INITIAL_PLANNING Template -> `liza add-tasks`

**Contract:** Rendered examples and instructions continue to create a bare JSON array accepted by `liza add-tasks`, with each entry carrying `id`, `desc`, `spec`, `done`, `scope`, `priority`, `depends`, `type`, and `role_pair`.
**Direction:** Orchestrator follows the wake instruction and runs `liza add-tasks --tasks-file <path.json> --agent-id <id> --json`.
**Invariants:** Simple goals create one specialized task. Fan-out goals create one master task when a fan-out target exists. Missing-master fallback creates one specialized task, not multiple specialized tasks.

## Data Flow

Explicit entry-point flow:

```text
state.Goal.EntryPoint
  -> pipeline entry-point specialized role-pair
  -> resolver maps specialized role-pair to optional decomposition-root role-pair
  -> wakeTemplateData resolved simple target + optional fan-out target
  -> INITIAL_PLANNING render
  -> liza add-tasks creates exactly one task
```

No explicit entry-point flow:

```text
pipeline entry-points
  -> sorted wakeEntryPointData list
  -> each entry includes simple target + optional fan-out target
  -> orchestrator classifies goal
  -> simple assessment selects specialized target
  -> fan-out assessment selects mapped master target when available
  -> liza add-tasks creates exactly one task
```

Missing-master fallback flow:

```text
entry-point specialized role-pair
  -> resolver returns no decomposition-root mapping
  -> wake data marks HasFanOutTarget=false
  -> template renders only specialized target for that entry-point
  -> orchestrator creates one specialized task even for broad work
```

## Cross-Cutting Concerns

| Concern | Approach |
|---------|----------|
| Error handling | Pipeline load and resolver inconsistency errors propagate from `buildWakeTemplateData` and prevent rendering. Missing master mapping is data, not an error. |
| Observability | The resulting task's `role_pair`, `type`, and ID prefix make the route visible in state and dashboard output. No new log stream is needed. |
| Configuration | All routing derives from frozen pipeline config and resolver metadata. No role-pair names are hardcoded beyond test fixtures. |
| Testing | Focused prompt tests cover explicit entry-point routing, classification data, master route availability, and missing-master fallback. |
| Backward compatibility | Frozen/custom configs without decomposition-root mappings continue to render a single specialized task route. |
| Security and invariants | State changes still go through `liza add-tasks`; input task type remains validated against role-pair doer role by existing ops code. |

## Structural Decisions

### Decision 1: Treat entry-point targets as simple targets

Entry-points remain specialized role-pairs because the same entry-point must support simple goals without creating a master task. This preserves Case B routing from the goal spec: entry points keep existing specialized targets, while INITIAL_PLANNING chooses the master only when fan-out is needed.

### Decision 2: Store fan-out targets beside simple targets

The template needs both possible destinations at render time. Storing both targets on the entry-point data avoids brittle name derivation such as replacing `-pair` with `-main-pair`, and lets custom role-pair names work.

### Decision 3: Missing master means single specialized fallback

For legacy/custom pipelines, no master route may exist. Rendering multiple specialized tasks would reintroduce the chimera risk this goal removes. The fallback therefore keeps one task and uses the specialized target to cover the full entry-point planning scope.

### Decision 4: Resolver errors fail rendering

An error from the resolver indicates broken topology or an impossible mapping state. Rendering a fallback in that case would hide a configuration defect. Only a clean "not found" mapping gets fallback behavior.
