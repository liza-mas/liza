## Goal

Pin every A7-produced frozen surface with black-box goldens, generated from the starting commit through
the SI-3 entry point, in two independent oracle packages: one for inspection output and `--json`
envelopes, one for installation and `state.yaml` effects.

## Context

Based on: the carrier `arch-scope7` and its direct references, the merged SI-3 refinement
`arch-harness`, the A7 source at integration HEAD, and the probes below, run against a `git archive`
export of starting commit `96c9ad69a` (its production tree equals integration HEAD, R1).

This document owns: the A7 surface inventory, its split into two oracle packages, the driver kind per
surface, the A7 environment and fixture conventions, and the determinism exclusions. SI-3 (tree
convention, golden form, adapter rule, ledger, entry point) stays at `arch-harness`; this plan
refines inside it and edits nothing it owns.

### Constraints

Inherited by reference: frozen-surface rules (`goal-frozen`), oracle immutability (`goal-tests`),
E2–E5 (`goal-proof`), G1.3/G1.4 (`guard-tier1`), assignment and depth (`arch-oracle-template`),
SI-3 H1–H7 (`arch-oracle`, `arch-harness`), shared-file rule for oracle files (`arch-files`).

New, local:
- **OC1** Test-only additions under `internal/oracle/a7/**`; no production file, existing test,
  harness file or `Makefile` changes (`arch-scope7` boundary).
- **OC2** Drivers are binary-driven by default: they import only the standard library and the
  harness, so they compile against the starting tree without an adapter and survive A3–A9 moves
  unchanged. An adapter is used only where no CLI invocation reaches the surface deterministically
  (three rows below, each named).
- **OC3** Linux only. Every A7 oracle test skips on other operating systems, naming the reason.
  Goldens are generated on Linux (the regeneration entry point runs in agent worktrees, E1), A7 has
  no build-constrained production file (R15), and Windows and macOS stay covered by the existing
  suites that N2 already runs. Rationale: generating goldens per platform cannot be done from the
  starting commit locally, and a golden that differs by platform would turn the macOS and Windows
  jobs red with no behaviour change.

## Components

| Component | Path | Responsibility |
|---|---|---|
| Inspection oracle | `internal/oracle/a7/present/` | Goldens for read-only A7 output and `--json` envelopes over a committed fixture project |
| Installation oracle | `internal/oracle/a7/install/` | Goldens for setup, init, activation, migrate and the TUI toggle: output, `state.yaml` before/after, installed trees, Git effects |

Both are test-only packages under the SI-3 tree convention (`arch-harness`), each owning its own
`testdata/fixtures/` and `testdata/golden/<kind>/`. They share no file. Key decisions:
- **Two packages, split by input shape**: inspection reads one fixture project; installation creates
  projects and homes from nothing. The split keeps each package's fixtures local, lets the two code
  plans proceed in parallel, and bounds each review.
- **Environment helper duplicated, not shared**: each package builds the A7 environment (below) from
  the standard library, about twenty lines. A shared helper would make one scope wait on the other.
  Ceiling: a third A7 oracle package extracts it into `internal/oracle/a7/internal/` in that task.

## Interfaces

**Harness → A7 packages** (`arch-harness` CONTRACT, consumed as is): CLI build helper, golden read
and compare per kind, normalisers, adapter rule, `write-new`. **A7 packages → regeneration entry
point**: discovered by path; the package filter `./internal/oracle/a7/...` bounds a run. **A7 oracle →
consumers**: Scope 17 (A7 refactor), Scope 18 (C4), Scope 21 (C6 init/migrate/TUI sites), and the A3–A6
refactors, whose `ops` changes reach `status` and `get` through X2 call sites (`arch-moves`); each runs
the packages live and changes no golden.

#### CONTRACT

**A7 conventions** (shared by both A7 oracle packages; tree, kinds and adapter rule per `arch-harness`):
- AC1 Linux only: each test skips on other systems, naming the reason. Goldens are generated on
  Linux, no A7 production file is build-constrained (R15), and other platforms stay under the suites
  N2 already runs.
- AC2 Drivers are binary-driven and import only the standard library and the harness; adapters
  exist only for rows marked adapter.
- AC3 Environment, built per test with nothing inherited: fresh temporary `HOME`, project root and
  `TMPDIR`; `PATH` is one directory holding a symlink to the host `git`; `LIZA_PROVIDER_CATALOG_URL=http://catalog.invalid/`
  (embedded catalog, no request, R3); `LIZA_SKIP_AUTO_UPDATE=1` (R17); `GIT_CONFIG_NOSYSTEM=1` and
  fixed Git author and committer names, emails and dates; other variables only where a row names
  them. Commands run in a temporary working directory or with `-C <temporary project>`, never in this
  repository or its `.liza/` (E4); no real provider CLI (E2). Failure messages carry names and paths,
  never values (G1.4).
- AC4 Clock and identity: fixture timestamps lie far in the past or future; now-relative values
  (`age`, `time_in_status`, `elapsed`, relative lease displays) are masked by key in `json` and by
  label in `human` goldens; `goal-<unix seconds>` ids are masked; fixture PIDs exceed Linux
  `pid_max`. These patterns are declared in the package and applied through the harness normaliser.
- AC5 Streams: stdout and exit code are recorded for every invocation; stderr too, except for codex
  activation, whose stderr carries a host-dependent AppArmor warning (R9).
- AC6 Excluded runtime files: `*.lock`, `*.lock.owner.json`, `log.yaml`, `alerts.log`,
  `~/.liza/cache/**`.
- AC7 Default brand only; `LIZA_` and `liza` literals are G1.3's "tests asserting default-brand
  behaviour" category.
- AC8 Goldens are created only by the entry point's `write-new` against the starting commit (E5);
  live tests compare and never create.

**Fixture project** (`testdata/fixtures/project/`): committed `.liza/state.yaml`, frozen
`pipeline.yaml` (the starting commit's default pipeline bytes) and the other `.liza/` files `status`
and `get` read, materialised by the test into a disposable Git repository with `main` and the
configured integration branch. The state is representative: tasks in executing, review, blocked
(with reason and dependencies), approved, merged and terminal states across at least two role
pairs; one task with history, rejection reason and output entries; agents of several roles with live
and stale heartbeats; anomalies; human notes; sprint metrics.
