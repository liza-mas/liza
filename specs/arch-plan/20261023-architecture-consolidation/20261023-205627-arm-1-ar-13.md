## Goal

Separate A4 planning and graph concerns inside ops, preserving observable behavior and the
existing application boundary, so later feature work has identifiable owners.

## Context and Decisions

Based on the supplied pinned authority and source probes below. Integration snapshot:
`6300af287f7330cc68f3b2ce7a46dd3fef2cd709`; initial branch `task/arm-1-ar-13`, clean.
The 23 A4 ratchet entries are two files and 21 functions, not 23 functions.
The architecture is prospective: A3 implementation and the A4 oracle implementation are
coding prerequisites, not claimed delivered functionality.

Design choice: retain `internal/ops` and its exported entry operations. Extract private
concern files/functions. This follows `adr-0021` and the A3 provider answer.
Alternatives considered: capability subpackages would move mutually used state/receipt/graph
helpers without an A4-owned K3 crossing; a generic transition/repair engine would hide
different atomicity and cleanup policies. Neither is required to satisfy S1/S3.
No new dependency, configuration field, public framework or query layer is planned.
Names of new private files and function signatures belong to code planning.

Existing classification/action types should be reused. Finite cardinality and lifecycle
vocabulary owned by A1/A3 is consumed, not redefined in A4. Ops-owned finite action/reason
sets become typed constants; other literal limits get names without changing their values.
YAML-defined identities stay open. K7 is applied in each concern, then reconciled in Scope 6.

No design uncertainty blocks this decomposition. Future acceptance receipts are not design
evidence. A failure of the promised provider contract when coding becomes eligible is
routed to that provider rather than silently changing this architecture.

## Proof and Shared Ownership

All six scopes are Must under `parent`. N3/N4 retain Should priority; no output waits on
Scope 26's optional coverage work. Default whole-phase inheritance is deliberate:
the generated code plans wait on upstream plans; their coding descendants inherit every A3
and A4-oracle coding prerequisite. Local output indexes form 0 → 1 → 2 → 3 → 4 → 5.
Thus the first A4 coding unit closes A3, and every remaining coding unit waits on that unit.
No provider implementation is required before writing a plan from its frozen contract.
No new cross-stage wait is needed; do not substitute prose-only waits or bypass inherited ones.

Five refactor writers share `internal/testguard/archguard/area_a4_test.go` and may update
the same invariant/schema/protocol references. The chain orders these non-commuting writes.
An additive private source/test file and a per-task acceptance manifest commute; updates to
the single guard literal and shared prose do not. Per-concern guard fragments were weighed
against five writers: changing that foundation-owned seam would widen scope, while document
writes still require ordering. The bounded area chain therefore remains appropriate.
Code planners order any additional overlapping coding writers. Do not split one deliverable
into a linear sequence solely by implementation steps; split by concern or named review risk.

Correction placement rule: after every started/merged writer and before every unstarted
consumer requiring the correction, select the earliest legal slot and declare its waits.
Re-weigh the seam with the correction included. A started required successor or no legal
slot needs a human ruling; do not reorder accepted writers silently.

Each refactor coding unit owns final acceptance through `make test`, `make lint`,
`make test-e2e`, and `go test -race ./internal/ops/`, extending race selection to X2-touched
packages. Use `env -i HOME="$HOME" PATH="$PATH" TMPDIR=/tmp` for environment-sensitive proof;
only disposable Git fixtures, no real providers or live runtime state. E1 overrides the
older generic lesson's full-repository race preference. Full make-test also runs A3/A8
oracle consumers once delivered. Every old golden and fixture remains unchanged except
an explicitly reviewed inherited exception. Preserve white-box assertions through moves.
Code plans map each touched frozen surface to delivered oracle cases and allocate uncovered
ones before the corresponding refactor. Added goldens follow SI-3 starting-tree provenance.

Proof stages: provider/oracle completion is an implementation prerequisite; E1, unchanged
oracles, white-box coverage and S1/S3 evidence are coding final acceptance. A3 G1-G8 is boundary
acceptance, with G8 held for the maintainer. Documentation-only architecture/code-planning
tasks do not run E1 as their own acceptance, so output validation arrays are omitted.
The exact regeneration command is prospective under foundation Scope 3; code plans probe
the delivered command rather than inventing it here.

Budget/isolation: the baseline records a green 444 s warm-up and a red 523 s timed test run
under shared-host load; neither is silently turned into a clean threshold. E1 plus ops race
is estimated at 15–35 minutes per refactor coding unit, five minimum units about 75–175 minutes
plus boundary evidence/review. These are estimates, not ceilings. Run proof serially within
each worktree to avoid concurrent generators. Three agent slots and 1800 s progress timeout
are observed; admission limits are unset. A 35-minute estimate does not prove it fits.
The code planner measures or sizes the acceptance timeout against the then-delivered admission
envelope; a mismatch uses the existing budget-ruling path, never skips proof. The 600 s command
cap requires waiting on the same foreground session until it finishes. G5 records Should
dispositions and baseline uncertainty without turning them into new Must gates.

Each concern updates references it invalidates in INVARIANTS.md,
`specs/architecture/{state-machines,blackboard-schema,supervision-model}.md`,
`specs/protocols/` and `lessons/`. Scope 6 records a new ADR/index entry for the durable
layout and vocabulary ownership. Historical ADRs, goal, contracts, skills, Makefile and
overview are not edited. Scope 1 owns justified A3 issue closures. A4 issue closures,
including `issue-proceed`, belong to the next boundary, not Scope 6.
Every scope permits its tests, additive oracle gaps and acceptance manifests.
