## Goal

Give review and anomaly policy one shared, pure provider-key derivation below ops, while keeping
tool identity at persistence, launch and presentation boundaries.

## Context

Based on assigned resolved references and source reads at integration/worktree HEAD
`4888b3926c9cbd974e859795f06877efb8848d95`. The source still contains pre-refactor locations:
A9's `agentlaunch` package is **PROSPECTIVE**, delivered by Scope 20's coding descendants before
this scope's coding through phase inheritance. Source paths below are discovery anchors, not
instructions to restore old locations. No production code is changed by this architecture task.

The registry already merges embedded and loaded catalogs, then configuration overrides. Policy
currently compares raw strings. The existing registry is therefore the needed seam; a second
catalog loader or hard-coded ACP suffix table would duplicate identity rules. The older review
and issue-registry recommendation to persist canonical provider values is superseded by the
explicit preservation rule in `changes`. Likewise the issue registry records the invariant text's
overstatement of verdict-time diversity: this scope retains ADR-0046's existing enforcement points.

#### CONTRACT

**Identity owner.** Extend the A9-owned `internal/agentlaunch` registry boundary with one pure
canonical-key query. Its inputs are a recorded tool name, the already-loaded catalog-derived tool
definitions and current project `AgentTools` configuration; its output is the effective provider
key specified by `parent`. Reuse the registry's merge/default semantics. No launch plan rendering,
executable discovery, environment-file loading, provider process or state write belongs in this
query. There is no new service interface or third-party dependency.

Keep the two identities separate: the recorded tool name addresses config, review-slot CLI/model
bindings, launch and display; the derived key addresses provider equality/grouping only. The
catalog-supplied key is overridden only as the current merge logic overrides it, including its
empty-versus-nonempty distinction. Match launch resolution's final whitespace handling; do not
invent lowercasing, suffix stripping, case folding or key aliases. A keyless unknown tool retains
its tool-name fallback; an unknown tool with an explicit key uses that key. Empty recorded identity
retains existing missing-provider behavior. Do not persist or migrate the derived value.

**Inputs and I/O.** Catalog acquisition stays with the existing loader/cache/fallback owner and
is prepared outside blackboard transactions. Capture the catalog-derived base once for an
evaluation, apply the config from the snapshot actually being evaluated, and share that pure
lookup across all its comparisons. In a locked claim/analyze operation, use the locked state's
configuration, not a stale preliminary config. Avoid per-agent catalog work. Keep existing catalog
failure/fallback behavior; an unknown persisted tool is not a new refusal. Do not create a new
network refresh or cache invalidation policy. This makes historical approvals and anomaly records
evaluate under current policy without requiring their agents still to be registered.

**Review data flow.** Recorded approval/agent tool names plus snapshot configuration and loaded
catalog -> canonical keys -> existing diversity predicates -> existing selection/merge result.
Ops owns canonical comparison in partially-approved preference, fresh-submission satisfiability,
doer/reviewer filtering and the alternative-reviewer pool. Runtime merge evaluation uses the same
query for approvals and reviewer-pool cardinality. Do not use the raw-only models helper as the
policy oracle; models must not acquire infrastructure imports. The code plan may keep that helper
as a raw utility or replace its call at the policy boundary, without expanding schema scope.

Identity equality is the only policy delta. Retain eligibility, capacity/lease and known-failed
validation checks, review-slot admission, priority tiers, missing-doer fallback, quorum count,
impact resolution and preferred-diversity fallback. In particular, aliases cease to count as
distinct providers; that does not turn preferred diversity into a hard merge or verdict refusal.
Persist approval provider strings exactly as before. Keep diagnostic formatting and raw identity
presentation separate from the comparison key; do not relabel an existing provider display merely
because its equality comparison is canonical now.

**Anomaly data flow.** Anomaly `Details["provider"]` tool names -> the same canonical lookup ->
provider-audit groups -> unchanged threshold, watermark/classification and response selection.
Use the identical lookup to select current registered agents belonging to each provider group.
Otherwise grouping aliases together while examining only one alias's health would produce an
incorrect HALT. Exact health provenance remains raw and generation-specific: agent ID, stored tool
name, PID and registration timestamp must still match the health record. Canonical equality must
never make another tool's stale health record valid for an agent epoch.

Analysis receives resolved identity inputs and remains pure. Its state-aware and anomaly-only
entry paths must agree when given equivalent identity/config inputs. The ops Analyze caller and
read-only watch prediction use that same path; API plumbing under X2 is allowed, but watch alert
throttling, mode gates and formatting stay unchanged. Keep original anomalies in returned evidence
and reports; do not mutate or rewrite their provider field. Non-provider grouping is untouched.
Only results necessarily changed by C2 grouping may differ. Existing unrelated human/JSON/TUI
content, labels and ordering remain governed by `frozen`.
