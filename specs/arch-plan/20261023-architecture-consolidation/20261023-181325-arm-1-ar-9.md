## Goal

One black-box oracle package for A9 that drives the real CLI binary against committed fixtures and
scripted stub providers, and pins every A9 surface listed below as goldens reproducible from the
starting commit.

### Constraints

Inherited by reference: frozen surfaces (`goal-frozen`); immutability and exceptions
(`goal-tests`); E2, E4, E5 (`goal-proof`); G1.3, G1.4 (`guard-tier1`); SI-3 H1–H7
(`arch-oracle`); harness tree, golden form, adapter rule (`ar0-harness`); surface assignment and
depth (`arch-oracle-template`).

New, local:
- **AC1 Test-only Go.** Every Go file the scope adds is a `_test.go` file in
  `internal/oracle/a9/`. No other `.go` file is added, under `testdata/` included, because the S1
  and K4 guards parse non-test Go files under `internal/` (`ar0-foundation`, parse-based import
  analysis). Stub-provider logic therefore lives in the test package (e.g. the test binary
  re-executed as the stub) or in non-Go scripts.
- **AC2 Binary-driven by default.** Drivers run the CLI built by the harness from the tree under
  test; they import only the standard library and the harness, so binary-driven rows have no
  adapter and A9 refactors (Scope 20, C6) never need a call-site-only edit for them. An
  adapter-driven driver (harness adapter rule) is allowed only for an inventory row whose success
  path cannot be reached through the binary from a committed fixture; the row then records
  "adapter" and the reason. Adapters call
  exported entry points only: `agent.RunSupervisor` with a scripted `agent.LLMAgent` (the e2e
  suite's precedent, R22) or an exported function of the row's producer (I-20).
- **AC3 Default configuration.** Fixture `config` keeps every default, including
  `lease_duration` 1800 and `heartbeat_interval` 60, so C1's default-config goldens stay valid. A
  scenario may set only the field that is its own trigger (e.g. `max_instances` for surplus). No
  scenario relies on idle max-wait to terminate (floor 300 s, R14).
- **AC4 Unix only.** The package skips on Windows with a stated reason: goldens are generated on
  Linux at the starting commit, scenarios use Unix process semantics and paths, and the stub
  executables are resolved through `PATH` as Unix executables. Windows-specific A9 behaviour stays
  covered by the white-box tests that move with the code (`goal-tests`).

## Design Decisions

- **Scenario model.** A scenario = committed input fixture → harness-built CLI run as
  `liza agent <role> --cli <tool> --agent-id <id>` (or another A9 entry, per row) in a disposable
  project → stub provider invoked by the supervisor → the supervisor exits on its own. Rationale:
  every A9 surface in the carrier is observable from the binary (R3–R12), and binary drivers
  survive Scope 20's restructuring without edits (AC2).
- **Deterministic termination.** A run ends by a scripted stub action, never a timer or signal:
  a quota or provider-unavailable line (R4, R5), `liza -C <root> stop` issued by the stub (R6), or,
  for multi-call scenarios, by the test after it observes the awaited state (R10). SIGTERM is
  excluded (R15); idle max-wait is excluded (R14).
- **At-launch snapshot.** Registration, heartbeat lease and claims are visible only while the
  supervisor runs (it unregisters on exit, R3). The stub copies `state.yaml` and any liveness
  record when invoked, while the supervisor waits on it, giving a consistent mid-run snapshot.
- **Committed fixtures, real Git.** Inputs are committed `.liza/` files plus a Git recipe the test
  replays in a temporary repository with fixed identity and dates, so commit SHAs are stable (R3).
  A fixture needing a later lifecycle state (e.g. `CODE_TO_REVIEW`) is derived once by running the
  starting-commit binary with a scripted stub (R11) and committed with its recipe note; it is an
  input, never regenerated by the entry point (E5).
- **Launch lines are recorded, not explained.** The executed command line diverges from
  `--explain-launch` (R7), so each tool's launch golden is the recorded sequence of stub
  invocations; `--explain-launch` output is a separate human golden of `liza agent` (assignment
  rule 1: no `ops` entry, content produced by `agent`).
- **Local normalisation layer.** Harness normalisers (`ar0-harness`) do not promise to keep lease
  durations or value identity. C1's asserted value is a duration, and C6/C3 goldens depend on
  which identifiers are equal. A9 therefore applies its own stdlib-only normaliser first (CONTRACT),
  then the harness's.
- **Fixed time zone.** The child environment sets `TZ` to a fixed non-UTC zone without DST, so
  local-time values are host-independent and distinguishable from UTC (`goal-frozen`: local
  timestamps stay local).

## Cross-Cutting Concerns

| Concern | Approach |
|---|---|
| Isolation | Each scenario owns its temporary repo, `HOME` and stub directory; no shared resource, so scenarios may run in parallel |
| Environment safety | Explicit child environment; messages carry names, paths and booleans, never variable values (G1.4); no live `.liza/` (E4); stubs only (E2) |
| Branding | Goldens record the default-brand build's output as it is (G1.3 structural category: tests asserting default-brand behaviour) |
| Failure reporting | A failed scenario names the inventory row, the golden path and the stage (setup, run, collect, compare) |
| Proof budget | Runtime basis: probes R3–R11 took 0–2 s per run (R9 includes a 2 s restart delay). Stage: every task's `make test` and the entry point at review and gates. Measured against H7 at gates (OQ-001) |
