## Goal

Separate A3's execution concerns inside `ops`, preserving its application-layer API and every
observable lifecycle effect while giving each concern a small, identifiable implementation.

## Context

Based on the supplied pinned parent and direct references, the A3 guard data, and source probes
RP1-RP10 below. The current worktree starts at `fe8c8e96ca4413364e45b4d36a92baafdae4e050` on
`task/arm-1-ar-12`, initially clean. This is architecture, not implementation: A2 refactoring and
A3 oracle coding are future prerequisites. Their approved contracts suffice for planning.

Design choice: keep the existing `ops` package, its exported entry points, and concrete error
types. Concern-named private files/functions separate phases and policy within that boundary.
Alternatives considered: a kernel sub-package would require moving many mutually used state and
receipt helpers and introduce migration work without an owned K3 crossing; a generic lifecycle
engine would obscure operations with different transaction/effect ordering. Neither is needed.
The existing claim strategies and claim-release descriptors already absorb real variation.

No new package, dependency, framework, configuration field or temporary forwarding API is planned.
Exported type changes are limited to K7 adoption with X2 caller conformance in Scope 5.
Behavior requirements are the referenced goal, not new definitions in this document.

## Proof and Shared Ownership

Every scope is Must (`parent`); no output depends on Scope 26's optional coverage feature. No
behavior change is included. N3/N4 retain Should priority. D23 is the effective E0 branch ruling.

All code-planning outputs use default `inherit_inputs`: their coding descendants wait for all
upstream coding children. Scope 1 thereby waits for every A2 coding unit and the A3 oracle units;
Scopes 2-5 additionally inherit the previous local scope's coding completion. This is the earliest
artifact sufficient for implementation under the mandatory area/oracle sequence. The plans may
be written once their upstream plans merge. No provider implementation is demanded before design.

Four A3 scopes write the single `area_a3_test.go` literal and may update INVARIANTS.md and related
code references. They are ordered 2 → 3 → 4 → 5. Scope 1 precedes them and writes the boundary
record/issue registry. Additive private Go/test files and per-task acceptance manifests commute;
ratchet literal deletions and shared reference edits do not. Per-scope guard-data fragments were
weighed against four writers: they require a change to the foundation-owned guard seam, while the
fixed one-file-per-area interface and actual shared-reference writes already require ordering.
Keep this bounded chain. Within each scope the code planner must order additional overlapping
writers; do not split a single deliverable into a linear series merely by implementation steps.

Correction placement: wait for every started/merged writer, precede every unstarted consumer
whose done_when requires the correction, take the earliest legal slot, and re-weigh the seam
against all writers including the correction. A started required successor or absent slot needs
a human ruling; no silent reordering or guard-code ownership change.

Proof allocation for every refactor coding task: `make test`, `make lint`, `make test-e2e`, and
`go test -race ./internal/ops/`, adding other touched packages for X2 changes. Run environment-sensitive
proof with `env -i HOME="$HOME" PATH="$PATH" TMPDIR=/tmp`; no real provider or live project state.
Full make-test also exercises the other areas' oracle consumers. Added cases are reviewed for
starting-tree provenance; old goldens/fixtures remain unchanged except the inherited exceptions.
White-box assertions move with their code and retain behavioral coverage. Source comparison and
phase-aware race tests cover lock and generation boundaries beyond CLI goldens.

Stage: oracles are implementation prerequisites; green E1 and immutability evidence are per-task
final acceptance; G1-G8 is boundary acceptance with G8 held for the maintainer. No full E1 run is
required to accept this documentation-only architecture. Never put these implementation suites
in the code-planning tasks' `validation[]`.

Budget: baseline warm-up 444 s and timed red 523 s are observations under shared-host load, not a
clean N4 threshold. E1 plus ops race is estimated at 15-35 minutes per refactor coding task;
four minimum concern tasks cost roughly 60-140 minutes, excluding boundary evidence and any
review/re-run. These estimates are not ceilings. Isolation is disposable Git fixtures; serial
proof in one worktree avoids competing generators. The 600 s foreground cap needs continuation
of the same tool process; no abandoned job. Config exposes no task admission budget here: each
code planner allocates a measured or explicitly estimated acceptance timeout within the delivered
admission envelope; use the existing budget-ruling path if it cannot fit, not a skipped suite.
The 1800 s progress timeout is not evidence that a 35-minute batch fits. G5 owner records N3/N4
dispositions and baseline uncertainty, with no Must gate promoted from those Should criteria.

Documentation: each refactor updates code references it invalidates in INVARIANTS.md,
