## Goal

Partition all production Go and the prompt templates into nine sequential ownership areas over a
fixed layer map, give every cross-area interface and shared file one owner, and order the run so
the S1 guard and baselines land first, every oracle merges before any refactor, and each C1–C6
change runs alone after its owning area's structural refactor.

## Context

Based on: the goal spec and decision record (direct references), the dated evidence documents
re-verified against the tree at the source revision (see Reality Probes), `go list` import graph,
a `go/parser` size measurement, `Makefile`, `.omni-ee/pipeline.yaml` (the run's pipeline:
master architecture → specialized architecture → code planning → coding), ADR-0048 phase-gate
inheritance, and direct reads of the C1–C6 sites.

This document owns: the area partition, the layer map and K4 rule set, the shared interfaces
SI-1…SI-5, cross-area rules, the area-boundary checkpoint contract, shared-file ownership, and the
cross-scope sequence and proof budget. Behaviour, constraints and proof environment stay at their
goal-spec anchors.

### Constraints

Inherited, by ID: Scope (`goal-scope`), Won't (`goal-wont`), Frozen Surfaces (`goal-frozen`),
C1–C6 (`goal-changes`), K1–K7 (`goal-structure`), test policy (`goal-tests`), concurrent changes
(`goal-concurrent`), N1–N4 (`goal-nfr`), E0–E5 (`goal-proof`), S1–S8 (`goal-success`),
documentation (`goal-docs`), failure modes (`goal-failures`), G1.1–G1.4 (`guard-tier1`), G2.2
(`guard-g22`), invariants (`inv-matrix`), ADR-0021/0045/0130/0177.

New, local to this plan:
- **MC1** Areas are ownership units, executed strictly one after another at the coding level;
  layers (SI-1) are dependency classes. An area may contain packages of several layers.
- **MC2** Every oracle merges before any structural refactor of any area (stronger than
  per-area): A1 and A2 sit below every frozen surface, so their refactor can break any surface.
- **MC3** A C-change's owning area is the last area in the sequence that contains one of its
  sites; it runs after that area's refactor and before that area's boundary checkpoint.

### Assumptions
- **ASM-001**: A sibling `depends_on` gates each generated level (architecture → code plan →
  coding) through phase-gate inheritance, so dependent planning may proceed once its upstream
  planning merged while dependent coding waits for upstream coding — *Why*: ADR-0048
  (`computeInheritedDeps`) — Confidence: HIGH.
- **ASM-002**: "The next area does not start until CI is green" requires areas to run one at a time
  at the coding level — *Why*: `goal-failures`, `goal-nfr` N1 stoppable at area boundaries —
  Confidence: MEDIUM.
- **ASM-003**: The run's starting commit is `112ccec9cd3a5f32003f043b6c06789cb0b4181e`, the
  integration-branch head when the run started — *Why*: probe P1 — Confidence: MEDIUM (the E0
  resolution may re-cut the branch; Scope 0 re-confirms and records the actual value).
- **ASM-004**: Planning artifacts of later areas may be authored before earlier areas' coding
  merges (ASM-001), so they can cite pre-refactor locations; coders follow the current tree and
  the Phase-consistency blocking rule (ADR-0048) — Confidence: HIGH.

## E0 Integration-Branch Hold

E0 (`goal-proof`) names the integration branch `refactor/architecture-consolidation`; the decision
record (`dec-branch` R7, `dec-next`) shows it was an agent-proposed name accepted with a set. The
run is configured with `global-refactoring` (P1), which is otherwise what E0 requires: a dedicated
branch cut from `main` (`97ccf330c`) at run start, agents never pushing.

Resolution belongs to the human; this plan does not choose:

| Option | Action | Cost |
|---|---|---|
| (a) | Amend E0 in the goal spec to name `global-refactoring` | One spec edit; no runtime change. Recommended: the branch already satisfies E0's intent |
| (b) | Integrate into `refactor/architecture-consolidation` (cut it from the current integration head, reconfigure `IntegrationBranch`) | Must happen before any child worktree is created from the old branch; in-flight tasks would need re-provisioning |

**Hold:** the first coding unit of the run (Scope 0, S1 guard unit) may not merge until the
configured integration branch equals the branch E0 names at integration HEAD. If they differ when
that unit starts, it marks BLOCKED with `--human-action` naming both options. Every other coding
task inherits this wait (all outputs depend on Scope 0). Scope 0 records the resolution and the
confirmed starting commit in the run baseline record.

The same unit also holds on OQ-003: `make sync-embedded` must leave the integration head's tree
unchanged. If it does not, the unit marks BLOCKED with `--human-action` asking the maintainer to
commit the synced copy; no task of this run commits it, since generated copies are outside every
scope.

**Owner:** Scope 0. **Consumers:** Scopes 1–9 (author), all refactor and C scopes (add, run,

## Cross-Area Rules

- **X1 Ownership.** A task writes only files of its own area, except under X2–X5.
- **X2 Call sites.** An area changing an API it owns updates every caller, in any area, in the same
  task, changing no caller logic. Oracle drivers follow under the call-site-only exception
  (`goal-tests`).
- **X3 Moves.** A move between areas is owned by the later area, after both areas' oracles merged.
  It edits the earlier area only to add or remove the moved symbols and their callers, keeps the
  earlier area's oracle green and its ratchet data unchanged or smaller, and never moves an S1
  offender still over threshold. New packages belong to the creating area.
- **X4 C sites.** A C scope edits its listed sites in any area (MC3).
- **X5 Urgent fixes.** The absorbing task is the next unstarted coding task of the area owning the
  touched files; if that area has none left, the next boundary-checkpoint unit. The maintainer
  names the fix commit to that task; a golden changes there only to the fixed value
  (`goal-concurrent`).
- **X6 Shims.** Type aliases and forwarders are listed in the area's plan (Shim Register) and
  removed before the area's boundary checkpoint passes; none crosses an area boundary.
- **X7 Typed vocabulary (K7).** The area owning the vocabulary's package introduces the typed
  constants and fixes callers (X2); later areas adopt them when refactored. Configurable sets
  (ADR-0045 role names) stay dynamic; no configuration field is added.
- **X8 Mutation logic** is not moved across the `ops` boundary except by C6 (SI-4).
- **X9 Behaviour.** No change outside C1–C6. A consolidation that would need one marks BLOCKED
  with `--human-action` (`goal-failures`).
- **X10 ADRs (K2).** A task that must contradict an accepted ADR writes the superseding ADR and
  marks BLOCKED with `--human-action` for approval before implementing the contradiction.
  Historical ADRs are never edited.

## Area-Boundary Checkpoint Contract

Executed by the boundary unit of area N: the first coding unit of the next area's refactor scope,
or of Scope 25 for A9. It inherits a wait on every coding task of area N, and every other coding
unit of its scope depends on it. Area N closes only when all hold:

| # | Check | Covers |
|---|---|---|
| G1 | Area N's ratchet data empty; remaining offenders only as S2 exceptions | S1, S2 |
| G2 | Area N's allowlist data holds only rationale-carrying entries; SI-5 crossings owned by area N resolved | K3, S6 |
| G3 | Area N's Shim Register empty | N1 |
| G4 | `make test`, `make lint`, `make test-e2e` green at integration HEAD; `go test -race` on area N packages | N1, E1 |
| G5 | Benchmarks (N3, indicative) and `make test` wall time (N4) measured against the baseline record; out-of-bound Should results, or a benchmark baseline that was not captured, get a recorded disposition and never block | N3, N4 |
| G6 | `architectural-issues.md` items resolved by area N closed with traceability (`issues-policy`) | Documentation |
| G7 | A new boundary record file (one per boundary) commits G1–G6 evidence | S7 |
| G8 | The unit marks BLOCKED with `--human-action`: the maintainer opens the integration→`main` PR and records the Linux/Windows CI result (macOS on the following `main` push). Green → unit completes. Red → the maintainer opens the fix task; the next area waits | N2, E1 |

A failed G1–G4 check is closure debt of area N, whose scopes are already complete: the unit marks
BLOCKED naming the failing check and area N, so the orchestrator commissions the repair in area N
(or the human rules); the unit never repairs area N's code itself and the next area waits.

## Systemic Decomposition Review

`systemic-thinking` run on the draft (2026-10-23). Findings and dispositions:

1. **STRESS POINT** — The critical path is nine sequential areas, a four-task C chain and nine
   maintainer PR/CI checkpoints (G8), with manual pipeline triggers between planning levels.
   Human latency multiplies along the chain. *Implication:* run duration is dominated by
   checkpoint latency, so an early stop at a boundary is a likely outcome. *Disposition:* accepted;
   it is the cost of N1/N2 as specified, and Scope 25 is defined to close out an early stop.
2. **LOAD-BEARING** — MC2 makes the slowest oracle scope gate every refactor. *Implication:* one
   stalled oracle halts the run. *Disposition:* accepted with rationale (A1/A2 underlie every
   surface); oracle scopes are independent and parallel, so the stall is local to one scope.
3. **CASCADE** — A1's exported API is consumed everywhere; X2 call-site sweeps from A1 touch every
   unrefactored area. *Implication:* A1 tasks carry repository-wide blast radius. *Disposition:*
   Scope 10 CONTRACT requires each exported-API change to name what it removes (K6).
4. **TENSION** — The boundary unit that verifies area N belongs to area N+1, whose owner cannot
   repair area N's closure debt. *Implication:* a failed check had no repair route.
   *Disposition:* the gate contract now blocks on failure and routes repair to area N.
5. **BLIND SPOT** — An absorbed urgent fix moves a golden away from starting-commit values, which
   would break provenance reproduction. *Disposition:* H1 reproduction baseline now includes
   absorbed fix commits.
6. **ASSUMPTION** — H1 requires reproducing in-process goldens (state effects, prompt builder)
   whose drivers follow moved APIs; feasibility is unproven. *Implication:* E5 provenance rests on
   Scope 0's harness design. *Disposition:* design prerequisite owned by Scope 0; every oracle and
   refactor scope waits on Scope 0.
7. **TRAJECTORY** — Per-area guard data named after run-scoped areas would persist as the
   permanent layer map. *Implication:* run scaffolding becomes structure future agents must
   interpret. *Disposition:* Scope 25 decides its post-run form.
8. **FRAGILITY** — C6, C1, C2, C3 all sit at the end of the longest chain; an early stop drops them
   while C2 corrects review-policy semantics. *Disposition:* accepted; MC3 and the layer order
   place them there, and the spec makes each C follow its area's refactor.
9. **ASSUMPTION** — Plans for later areas are authored before earlier areas' coding merges
   (ASM-004) and can cite moved locations. *Disposition:* accepted; coders follow the tree and
   the ADR-0048 phase-consistency rule.
