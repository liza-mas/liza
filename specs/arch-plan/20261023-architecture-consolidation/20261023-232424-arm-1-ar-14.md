## Goal

Separate A5's review and acceptance concerns inside `internal/ops`, with unchanged observable
behaviour and lock discipline, so the A5 ratchet empties and later work finds one owner per concern.

## Context and Decisions

Based on the pinned references above, source reads and the probes in Reality Probes, at
integration `3e85b4628231e03f38b958d7114fd8b093c3f423` (branch `task/arm-1-ar-14`, clean).
The `internal/ops` production tree there equals the starting commit `96c9ad69a` (RP1).
The A5 ratchet holds 6 files and 12 functions (RP2). The A4 refactor, the A5 oracle and the SI-3
regeneration entry point are PROSPECTIVE providers; this plan does not claim them delivered.

**D-1 Package layout.** A5 stays in `internal/ops`, keeps its exported entry operations and result
types, and extracts private concern files and functions. Rationale: `adr-0021` and the A3/A4
precedent (`a3-kernel`); A5 code calls A3 kernel helpers (`lifecycleMutation`,
`modifyLifecycleState`), A4 helpers (`validateBoundedContractCorrection`,
`checkPlanningOutputSnapshot`) and A6 locks (`withIntegrationMutationLock`,
`withEffectiveIntegrationCompletionLinearization`). Rejected: an `ops/review` sub-package, which
would export those helpers or create cycles without an S1/S3 need and with no A5-owned K3 crossing
to resolve (`crossings`). No new package, so A5 layer and allowlist data stay empty.

**D-2 Concerns, not engines.** Each offender is reduced by separating phases it already has:
precondition read, Git and command work outside the lock, the final transaction, and result or
anomaly projection. Rejected: a generic "await" or "lifecycle step" framework over
`await_verdict` and `await_resubmission`. Their ownership, reservation and finish policies
differ, and K6 admits a shared helper only where a code plan names the duplicated lines it absorbs.

**D-3 One code plan, ordered coding units.** The A4 boundary unit and the five concern units form
one code-planning Scope. The planner orders the coding units. Rationale in `a5-proof`. In short,
every unit writes the non-commuting A5 guard literal and the chain-serialized documents. An order
between the coding units of sibling code plans can only be declared today as a planning-order
edge (`planning-order-ruling` records why), and D30 waives that pattern for Scope 13 only.

**D-4 K1 is non-regression** (`k1-ruling`): the inherited Git calls inside A5 transactions are
listed in K1 Inherited Exceptions. They stay in their transaction with the same checks, order and
refusals. No refactor adds a Git or `exec` call inside a `Modify`.

**D-5 Known registry issues stay open.** `issue-clean-worktree` and `issue-verdict-diversity`
describe behaviour changes outside C1–C6 (`goal-wont`, X9). A5 preserves the current behaviour and
leaves both issues open.

Assumptions:
- **ASM-001**: Default phase inheritance (ADR-0048, as in `a4-proof`) holds this output's code plan
  on the upstream plans of `arm-1-ar-13` and `arm-1-ar-5`, and its coding units on their coding
  descendants. So the A4 refactor and the A5 oracle are delivered before the boundary unit runs.
  *Why*: same mechanism and wording as the merged A4 plan. Confidence: HIGH.
- **ASM-002**: The A5 oracle is delivered as `a5-oracle` specifies. At probe time its code plan
  `arm-1-ar-5-cp-0` is BLOCKED on a harness run-helper incompatibility (RP9). The fix belongs to
  that task and the Scope 0 harness owner. This plan's coding stays held by ASM-001 until then.
  Confidence: MEDIUM on timing, HIGH on the hold.

Open questions: none blocking. A change to the oracle contract made while unblocking the oracle
is consumed through `a5-oracle`'s owner. A refactor never substitutes its own harness.

Rules for every concern:
- A private helper that runs inside a transaction receives the state, task and context it needs.
  It never opens a blackboard, task, integration or file lock. The operation keeps its lock order,
  transaction boundaries, error identity and effect order.
- Extracted validation adds no check, does not change which refusal comes first, and swallows no
  error.
- Generation fencing, request identity and receipt replay come from the A3 kernel (`a3-kernel`,
  `adr-0130`).
- Exported operations, result types and their JSON fields are preserved (`goal-frozen`).
  Renaming an owned API is allowed only with X2 caller updates that change no caller logic.

## Proof and Shared Ownership

Priority: the single output is Must (`parent`). N3 and N4 stay Should and never block.
No output waits on optional Scope 26.

**Writer analysis (D-3).** The expected writers are the boundary unit and five concern units.
- The boundary unit writes only `specs/architecture/consolidation-run/boundary-a4.md` and
  `specs/architecture/architectural-issues.md`.
- Every concern unit removes its own ratchet keys from `internal/testguard/archguard/area_a5_test.go`.
  The guard fails on a stale entry (RP4), so the removal lands in the same commit. Entries of
  different concerns are interleaved in one literal, so these edits do not commute.
- Concern units update the A5 code references in `INVARIANTS.md` (29 references to A5 files, RP8)
  and possibly `specs/architecture/{state-machines,blackboard-schema,supervision-model}.md`,
  `specs/protocols/` and `lessons/`.
- All concern units also share one Go package namespace for new private names.

An additive seam was weighed and rejected. Per-concern guard data files would change the
foundation-owned per-area seam (`size`, `shared-files`). Document references would still need
ordering.

The units therefore run serially in one code plan: the boundary unit first, every other unit
depending on it, and the concern units in a chain. Recommended order: K-ACC, K-SUB, K-VER, K-AWT,
K-OWN. Acceptance helpers are consumed by submission, claim and reclaim, and claim-boundary helpers
are consumed by reclaim. The planner may reorder with a stated reason. It may merge concern units
only under the per-task fixed-cost rule, and splits only for a named review risk or a diff too large
to review. The last unit owns the closure duties in Scope 1.

**Correction placement.** A later correction writer goes after every started or merged unit and
before the unstarted units its done-when names, at the earliest such slot, with its waits
declared. If no legal slot exists, or a successor it requires has started, it needs a human ruling.

**Proof per coding unit.** Final acceptance is `make test`, `make lint`, `make test-e2e` and
`go test -race ./internal/ops/`, with race extended to packages touched under X2.
- Environment-sensitive proof runs under `env -i HOME="$HOME" PATH="$PATH" TMPDIR=/tmp`, on
  disposable Git fixtures only, with no provider CLIs and no live `.liza/` state (`goal-proof`, G1.4).
- The A5 oracle and every other delivered oracle run live with goldens unchanged, except reviewed
  `goal-tests` exceptions.
- White-box assertions survive moves.
- Added coverage follows SI-3 starting-tree provenance (`oracle`).

**Stages.** The A4 refactor, the A5 oracle and SI-3 regeneration are implementation
prerequisites, held by ASM-001. E1, unchanged oracles, K1 non-growth, white-box coverage and S1/S3
evidence are coding final acceptance. A4's G1–G8 is boundary acceptance, with G8 held for the
maintainer. The architecture and code-plan tasks run no E1 themselves.

**Budget and isolation.**
- `baseline` records a green 444 s warm-up and a red 523 s timed `make test` under host load.
  Neither becomes a threshold.
- E1 plus ops race is estimated at 15–35 min per coding unit, so about 1.5–3.5 h for six units.
  These are estimates, not measurements.
- Proof runs serially within a worktree. Observed config: 3 instances, a 1800 s progress timeout,
  admission limits unset (RP6).
- The 600 s command cap means waiting in the foreground on the same session until it finishes.
- A misfit with a later admission envelope goes through the existing budget-ruling path. Proof is
  never skipped.

**Documentation.**
- The concern units update the A5 code references they invalidate.
- The last unit records one new ADR (next free number, with its index row) for the A5 concern
  layout, the vocabulary ownership and the K1 exception inventory under `k1-ruling`.
- Not edited: historical ADRs, the goal, contracts, skills, `Makefile`,
  `specs/architecture/overview.md`.
- A5 issue closures belong to the A6 boundary. The boundary unit closes only A4 items, with
  traceability (`issues-policy`).
