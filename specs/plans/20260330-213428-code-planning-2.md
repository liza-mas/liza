## Task 1: Implement `handleAwaitVerdict` MCP handler

**Intent:** Add the MCP handler function that extracts parameters, delegates to `ops.AwaitVerdict`, and formats the response.

**Design:**

```go
func (s *Server) handleAwaitVerdict(params map[string]any) (any, error)
```

**Parameter extraction:**
- `task_id` — required string, via `requireString(params, "task_id")`
- `agent_id` — required string, via `requireString(params, "agent_id")`
- `timeout_seconds` — optional float64 (MCP transmits integers as float64), default 1500s (25 min, within Claude Code's 30 min `MCP_TIMEOUT`)

**Delegation:**
```go
result, err := ops.AwaitVerdict(context.Background(), s.projectRoot, taskID, agentID, timeout)
```

**Error handling:**
- `ErrBudgetExhausted` → return `textResult("Budget exhausted: ...")` (not an error — informational)
- Other errors → wrap with `"await verdict failed: %w"`

**Response formatting:**
```go
msg := fmt.Sprintf("Verdict: %s\nStatus: %s\nReason: %s\nReviewer: %s",
    result.Verdict, result.TaskStatus, result.Reason, result.ReviewerAgent)
if result.Guidance != "" {
    msg += fmt.Sprintf("\n\n%s", result.Guidance)
}
return textResult(msg)
```

**Key design notes:**
1. `context.Background()` is used because MCP handlers don't receive a context from the protocol layer. The `ops.AwaitVerdict` function handles its own deadline via the `timeout` parameter.
2. `ErrBudgetExhausted` is returned as a success response (not an error) because it's an expected outcome — the agent should exit normally, not retry.
3. `Guidance` (rejection feedback) is appended only when non-empty, preserving clean output for non-rejection verdicts.

**Scope:** `internal/mcp/handlers_mutation.go`

**done_when:** `handleAwaitVerdict` method on `*Server` extracts `task_id` (required), `agent_id` (required), `timeout_seconds` (optional, default 1500), calls `ops.AwaitVerdict(context.Background(), ...)`, returns formatted text with Verdict/Status/Reason/Reviewer on success with Guidance appended when non-empty, returns `textResult` with budget message on `ErrBudgetExhausted`, wraps other errors; `go build ./internal/mcp/...` succeeds.

**spec_ref:** Spec step 2 "MCP handler"

## Task 2: Register `liza_await_verdict` tool and add claude-settings permission

**Intent:** Wire the tool definition into `registerMutationTools` and enable auto-approval in claude-settings.json.

**Design — Registration (`server_registration.go`):**

Add to the `registerMutationTools` `toolDef` slice, after `liza_submit_for_review`:

```go
{
    tool: protocol.Tool{
        Name:        "liza_await_verdict",
        Description: "Block until review verdict arrives for a submitted task. Budget-aware: refuses if iteration limit would be exceeded on rejection. Call after liza_submit_for_review.",
        InputSchema: protocol.InputSchema{
            Type: "object",
            Properties: map[string]protocol.Property{
                "task_id":         {Type: "string", Description: "Task ID to await verdict for"},
                "agent_id":        {Type: "string", Description: "Agent ID (for authorization)"},
                "timeout_seconds": {Type: "integer", Description: "Max wait time in seconds (default: 1500, must be < MCP_TIMEOUT)"},
            },
            Required: []string{"task_id", "agent_id"},
        },
    },
    handler:     s.handleAwaitVerdict,
    roleChecker: operationChecker(s.resolver, s.pipelineLoadErr, "liza_await_verdict"),
}
```

**Key design notes:**
1. `operationChecker` gates the tool to roles that have `await-verdict` in their `allowed-operations` (all doer roles, per CP1's pipeline config).
2. `timeout_seconds` is declared as `"integer"` in the schema (MCP JSON Schema type), though the handler receives it as `float64` from JSON deserialization.
3. Placement after `liza_submit_for_review` follows the natural workflow order (submit → await).

**Design — Settings (`claude-settings.json`):**

Add `"mcp__liza__liza_await_verdict"` to the `permissions.allow` array, alongside the other liza tool permissions:

```json
"mcp__liza__liza_await_verdict",
```

This goes after `"mcp__liza__liza_submit_for_review"` (workflow order).

**Scope:** `internal/mcp/server_registration.go`, `internal/embedded/claude-settings.json`

**done_when:** `liza_await_verdict` appears in `registerMutationTools` with InputSchema having `task_id` (string, required), `agent_id` (string, required), `timeout_seconds` (integer, optional); handler is `s.handleAwaitVerdict`; roleChecker is `operationChecker` for `"liza_await_verdict"`; `"mcp__liza__liza_await_verdict"` is in `claude-settings.json` `permissions.allow` array; `go build ./cmd/liza-mcp/...` succeeds.

**spec_ref:** Spec step 3 "Register tool" and step 7 "Tool permission"

**depends_on:** Task 1 (handler method must exist for `s.handleAwaitVerdict` reference to compile)

## Task 3: Add handler-level tests for `handleAwaitVerdict`

**Intent:** Test the MCP handler's parameter validation, role enforcement, and successful verdict flow.

**Design:**

Tests go in `internal/mcp/handlers_await_verdict_test.go` (dedicated file) and/or `internal/mcp/handlers_test.go`:

**Test cases:**

1. **`TestHandleAwaitVerdictMissingTaskID`**: Call handler with `agent_id` only → error mentioning "task_id"
2. **`TestHandleAwaitVerdictMissingAgentID`**: Call handler with `task_id` only → error mentioning "agent_id"
3. **`TestHandleAwaitVerdictTaskNotInAwaitableStatus`**: Call with valid params on a task in READY status → error "await verdict failed" (precondition failure from ops layer)
4. **`TestHandleAwaitVerdict_RoleCheck`**: Access via registered handler (`server.handlers["liza_await_verdict"]`) with orchestrator agent → error "not allowed for role orchestrator"
5. **`TestHandleAwaitVerdict_Success`**: Set up task in CODE_READY_FOR_REVIEW with submission history; in goroutine, transition to approved after delay; call handler → result contains "Verdict:" and "Status:" (uses `testhelpers.WaitForAsyncSetup()` pattern)

**Test patterns:**
- Use `setupTestWorkspaceWithGit(t)` for workspace setup
- Use `NewServer(projectRoot, logPath)` for server creation
- Use `testhelpers.CreateValidState()` + `testhelpers.BuildTaskByStatus()` for state setup
- Use `testhelpers.WriteInitialState(t, statePath, state)` for blackboard initialization

**Key design notes:**
1. Tests 1-3 call the handler method directly (`server.handleAwaitVerdict(params)`) — these test parameter extraction and ops-layer preconditions.
2. Test 4 calls through the registered handler (`server.handlers[...]`) to verify the roleChecker middleware.
3. Test 5 requires a goroutine to transition task status because the handler blocks; uses short timeout (10s) and `testhelpers.WaitForAsyncSetup()` for reliable timing.
4. `ErrBudgetExhausted` is tested at the ops level (CP1 scope); the handler's pass-through (`textResult` with budget message) is implicitly validated via the success test pattern.

**Scope:** `internal/mcp/handlers_test.go`, `internal/mcp/handlers_await_verdict_test.go`

**done_when:** Tests pass for: (1) missing task_id returns error mentioning "task_id", (2) missing agent_id returns error mentioning "agent_id", (3) non-awaitable task status returns "await verdict failed" error, (4) orchestrator role rejected by registered handler role checker, (5) successful APPROVED verdict returns formatted text with "Verdict:" and "Status:"; `go test ./internal/mcp/... -run TestHandleAwaitVerdict` passes.

**spec_ref:** Spec step 8 "Tests — handlers_test.go"

**depends_on:** Task 2 (tool must be registered for role check test via `server.handlers["liza_await_verdict"]`)
