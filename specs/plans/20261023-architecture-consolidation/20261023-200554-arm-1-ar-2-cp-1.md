### Fixture and execution rules

Use the delivered harness BuildCLI once for `./cmd/liza` (structural module path,
permitted default-brand category). Run every observation through that binary. Use the
delivered Run options where they support the fixture lifecycle; a pipe-driven ACP interaction
may use stdlib exec of that same binary with harness ChildEnv and explicit cleanup.
Do not invoke the installed orchestration binary. No host provider/index/installer process
may be selected.

Use a disposable root per case with separate home, project, tmp, bin, store, install and
global directories. CLI PATH contains only committed fixture stubs, with a link to host git
only where required. Fixture scripts use an absolute interpreter. For an installed index
script's ordinary shell utilities, supply committed fixture wrappers with fixed absolute
utility paths; do not append a host PATH directory or expose real provider/index commands.
Resolve Go and git once before restricting fixture PATH.
The ACP fixture build is a Go-toolchain child using harness ChildEnv with its Go policy;
it does not run with the CLI's restricted PATH.

The driver must not assume the harness Run default PATH is isolated: harness-plan D-6
defaults to host PATH. Supply the supported fixture PATH option; if unavailable, construct
the command with ChildEnv using the fixture Path field. Never redefine a policy name via
ChildEnv extras (D-14 rejects that). HOME/TMPDIR/project and optional global/install/store
locations stay disposable. Omit SHELL and host agent identities, feature flags, proxy,
provider, Git configuration and secret-bearing values. Use only explicit known fixture
metadata; failed assertions report variable names/booleans, never a host environment.

Any setup adapter that reads process environment runs serially with temporary fixture
environment overrides restored by cleanup, including Git configuration isolation.
A fixture-directory git link and GIT_CONFIG_NOSYSTEM=1 prevent global configuration leakage.
No live runtime state is read. No tests are parallelized while process-global environment
is temporarily changed. RPC exchange order uses pipes/acknowledgements, never sleeps.

Case implementation details needed beyond row allocation:

  uses a deliberately unreachable loopback endpoint; no catalog request may use the default

### Normalisation and provenance

Use only the shared harness normalisers/comparators. Register disposable paths, exact
loopback ports and event/session identifiers; preserve stable catalog values, status/error
codes, metadata, digests' semantics, content sizes and output ordering. Never replace
non-deterministic output with empty strings or discard fields to make a golden pass.

For artifact comparisons, apply the harness's narrowly scoped volatile substitution before
the raw artifact comparator when the row explicitly requires it (e.g. cache fetch time,
temporary directory references, random event names). Do not whitespace-normalise artifact
bytes. Sort file inventory by normalized relative path; avoid overwriting entries when
distinct random event filenames normalize to the same token (assign stable occurrence
tokens within the known scripted sequence). Validate each recorded file and the complete
inventory. Goldens contain no host-derived value. Default-brand strings are deliberate
default-brand assertions under AC4; no separate CLI branding mode is introduced.

Write goldens only with the inherited entry point's `write-new` mode filtered to
`./internal/oracle/a2/cli/...`; then run canonical `check`. Never generate expected
values from integration production code or invoke ORACLE_WRITE directly as provenance.
Commit fixtures, drivers and goldens. A missing live golden fails. No PROVENANCE record is
added for new goldens; the foundation owns its start record. If an existing golden or
production surface would need changing, stop and route the conflict to its owner.
The starting commit is `96c9ad69aee983ce2b929dd681b6ba43bf920535`; absorbed-fix handling
remains the entry point's contract.
